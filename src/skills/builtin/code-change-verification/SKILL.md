# 代码改动验证

这个技能只在**确实改了代码**时使用。只改文档、只回答问题、或者还在讨论方案时，不要跑整套检查。

## 先看清楚再跑

1. 用 `glob` 或 `read_file` 找到本次改动涉及的文件。
2. 读 `package.json`（或 `Makefile` / `pyproject.toml`）里的 scripts，确认实际命令，不要凭印象拼。
3. 判断影响面：
   - 只改一个模块：先跑针对它的测试，再跑全量类型检查。
   - 改了公共类型、导出、配置：类型检查、lint、全量测试都要跑。
   - 只改文档：不跑测试，最多检查链接和代码块。

## 顺序

按仓库自己的顺序，通常是：

1. 格式化 / lint
2. 类型检查
3. 测试

不要跳过类型检查直接跑测试；类型错误会让测试结果失去意义。不要一次开很多命令然后等它们互相干扰。

## 失败时

- 只修和本次改动相关的问题。不要顺手重构、不要改无关测试来让它变绿。
- 如果失败是环境问题（缺依赖、端口被占、没有 key），明确说出来，不要把它伪装成代码失败。
- 如果一个检查跑不了，报告“没跑”和原因，不要写“应该没问题”。

## 报告

结束时用一小段说清楚：

- 跑了哪些命令；
- 每个命令的结果（通过 / 失败 / 没跑）；
- 如果失败，失败在哪、你改了什么、还有什么没解决。

不要用“全部通过”概括一个你没真正跑过的检查。
