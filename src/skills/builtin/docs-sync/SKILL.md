# 文档同步检查

文档过时不是排版问题，是会让人按错误的方式使用系统的缺陷。目标是找出**与代码不一致的具体句子**，而不是重写整篇文档。

## 先找真实行为

1. 用 `grep` / `glob` 找到这次改动涉及的入口：命令、配置、API、导出。
2. 读代码，不要只读文档。文档里写的命令，要能在 `package.json` / `Makefile` / CLI 里找到。
3. 特别检查：
   - 环境变量名和默认值；
   - 命令名、参数、退出行为；
   - API 路径、请求字段、响应字段；
   - 文件路径和目录结构；
   - 已经删除的功能是否还在文档里。

## 再对照文档

按这个顺序：

1. `README.md`：快速开始和命令表最容易腐烂。
2. `docs/adr/`：决策是否被后续实现推翻，ADR 是否记录了替代方案。
3. `CHANGELOG.md`：新改动有没有记录；已知限制是否仍然成立。
4. 代码注释和工具描述：它们也是模型读到的文档。

## 输出

按文件列，不要笼统说“文档需要更新”：

```text
README.md:42 — 命令表还写着 npm run old-command，代码里已经是 npm run new-command
docs/adr/014 — 说写入默认关闭；实际默认仍是关闭，这条是对的，不用改
```

每条给出：文件、行号、现在的说法、真实行为、建议改法。

## 边界

- 先报告，不要直接改文档；用户确认后再动。
- 不要为了“让文档更完整”而扩写背景；只修不一致和缺失的关键信息。
- 不要把代码注释里的历史解释删掉——它们往往记录了为什么，而不是是什么。
