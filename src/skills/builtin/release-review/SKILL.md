# 发布前审查

目标不是把整个 diff 复述一遍，而是回答一个问题：**现在能不能发，如果不能，具体缺什么。**

## 找到比较基线

1. 用 `git describe --tags --abbrev=0` 找上一个发布 tag；如果仓库没有 tag，明确说出来，并改为和 `main` 的上一个发布提交比较。
2. 用 `git diff --stat <tag>..HEAD` 看规模，再按目录看关键改动。
3. 不要因为 diff 很大就跳过；先看导出、公共 API、配置、迁移和依赖，再看实现细节。

## 检查什么

按这个顺序：

1. **兼容性**：导出的类型/函数签名、构造参数、配置字段、CLI 参数、API 路径。
2. **数据**：有没有 migration；migration 是否可回滚；旧数据在新的读取路径下还能不能读。
3. **依赖**：新增/升级的依赖，尤其是 major 版本、删除的运行时支持、锁文件变化。
4. **回归**：测试覆盖了没有；有没有“改了行为但没改测试”的地方。
5. **发布说明**：breaking change、迁移步骤、已知问题是否写清楚了。

## 输出

先给结论，再给证据：

```text
发布结论：可以发 / 暂缓
原因：一句话
范围：X files, +A/-B
```

然后列出：

- 阻断项（如果有）：具体文件、具体风险、需要做什么才能解除；
- 非阻断项：建议但不阻塞的问题；
- 没验证的部分：明确说出来，不要用“应该没问题”代替。

## 边界

- 不要替人做发布决定；你给的是证据和建议。
- 不要在审查过程中改代码，除非用户明确要求。
- 不要把 diff 里的大段代码贴回来；引用文件、行号和关键片段就够了。
