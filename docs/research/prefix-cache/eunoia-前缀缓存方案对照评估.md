# Eunoia 前缀缓存方案对照评估

> 日期：2026 年 11 月 8 日。状态：完成短回复对照及其 20 轮延长实验，并补做真实长回复逐字回填的 16 请求复测；未修改生产请求组装逻辑。

## 修正后的结论

**值得继续设计前缀稳定的模型会话记录，不能再用前两次实验支持“不值得改”的一般判断。** 用户指出真实请求应携带 assistant 后，核对发现：之前虽然携带了 assistant，但全部替换成“已记录，请继续。”，没有回填 API 实际输出。因此漏测了长回复的缓存复用收益，之前由此推导项目优先级的结论过宽。

补做真实长回复回填实验后，完整保留旧背景在该场景下累计输入费用减少 **32.07%**，第 4 轮单次输入费用减少约 **41.13%**，累计输入长度仅增加 **5.96%**。这是值得重视的收益。含实际输出的累计总费用减少 **12.46%**，不能把输入费用降幅当成总账单降幅。

实施方向应是保留真实模型输入/输出的顺序与内容、明确动态状态的作用域，并在窗口预算要求时建立压缩边界。本次仅完成评估，未修改生产代码，也不证明可以永久重放所有旧 system 背景。收益取决于回复与背景长度、供应商缓存行为和价格，不能承诺越长就无限变好。

进一步对照 Codex、Claude Code、DSH 和 OpenCode 后，建议把“可恢复的模型轨迹、状态变化追加、明确压缩边界”列为近期基础改进。源码依据、最小实施范围及验收见 [主流 Harness 实现对照](eunoia-前缀缓存与主流Harness实现对照.md)。

实施采用 DSH 与 Codex 的组合参考，排除 OpenCode 作为实施方案。执行入口：[交给 DSH 的实施清单](../../plans/eunoia-模型轨迹与前缀缓存实施清单.md)；讲解入口：[当前能力与亮点介绍](../../features/eunoia-前缀缓存与模型轨迹亮点介绍.md)。新增方案仍待实现，本文实测是已有对照脚本的结果。

## 为什么 assistant 会改变判断

项目的 `buildRunInput()` 本来就携带历史 user 和 assistant。问题出在实验的 assistant 太短、且不等于上轮真实输出，并不是项目漏传了 assistant。

忽略稳定提示词后，第一轮实际输入和输出是：

```text
输入：user₁ → 动态背景₁
输出：assistant₁（例如约 1000 Token）
```

当前方案第二轮变成：

```text
user₁ → assistant₁ → user₂ → 动态背景₂
```

完整保留则是：

```text
user₁ → 动态背景₁ → assistant₁ → user₂ → 动态背景₂
```

当前方案删除了先前位于 assistant₁ 前面的动态背景₁，改变了前缀，因而难以沿用该完整前缀下的 assistant₁ 缓存。保留顺序则有机会复用上轮输入和输出形成的前缀；是否命中以服务端 usage 为准。更早的 user/assistant 仍可能已经存在于上轮输入缓存中，不能说当前方案每轮都会重新计算全部历史回复。

如果 assistant₁ 只有几个 Token，这部分损失很小；若它有数千 Token，就可能超过多保留一份背景的成本。前两次实验只覆盖了前者。

## 真实长回复复测

采用两个 4 轮对照组，第二组反转方案执行顺序，共 16 次真实 `deepseek-flash` Responses 请求。每轮让模型复制固定 48 条合成检查项并返回当前目录和命令许可；每次实际输出 1025–1030 Token，下一轮逐字回填该实际输出，而不是替换成固定占位文本。脚本逐轮断言 assistant 数量及内容一致；第 4 轮已携带 3 条 assistant，合计约 5338–5379 字符。

复测仍调用项目真实上下文构建函数，加载稳定系统提示词；未发送工具声明、未执行工具，关闭 thinking，不启用 JSON response-format。单次输出上限 2048 Token，最多 16 次请求、200,000 输入 Token；实际输入 92,982、输出 16,424 Token。没有使用用户会话内容。

| --- | ---: | ---: |
| 请求数 | 8 | 8 |
| 累计输入 Token | 45,146 | 47,836 |
| 累计缓存命中 Token | 25,088 | 34,560 |
| 累计未命中 Token | 20,058 | 13,276 |
| 加权缓存命中率 | 55.57% | 72.25% |
| 累计输出 Token | 8,220 | 8,204 |
| 输入参考费用 | $0.003083964 | $0.002095080 |

| 首字延迟中位数 | 724.5 ms | 664.5 ms |
| 当前状态及完整检查项语义校验 | 8/8 | 8/8 |
| 严格 JSON 格式及布尔类型校验 | 4/8 | 4/8 |

参考费用使用下文同一 Flash 非高峰费率，不代表实际账户扣费。累计多发送 2690 个输入 Token，减少 6782 个未命中 Token，输入费用下降 32.07%。两组中同一方案的 usage 接近，但样本仍小，延迟不能作稳定提速承诺。

第 4 轮按两组平均：当前输入 **8785**、命中 **6272**、未命中 **2513**；完整保留输入 **9456**、命中 **8064**、未命中 **1392**。即输入增加约 7.64%，该轮输入费用从 $0.000395766 降至 $0.000232992，减少约 41.13%。这与短占位回复的 20 轮结论不同，说明回复长度确实是关键变量；它还不是一个真实长回复的 20 轮实验。

校验说明：原提示词未要求 commands 必须是布尔类型，有一组返回“是/否”；另一组带了 JSON 代码围栏。两者均按保存的原始输出重新进行语义校验，目录、许可与 48 条内容均正确。原严格检查保留在 `strictFormatCorrect`，没有把格式失败算作陈旧权限错误，也没有改写回填给下一轮的原文。两种方案严格检查都是 4/8；这不是任务质量或权限安全的完整评测。

## 比较的两个方案

**当前方案**使用项目的 `buildRunInput()` 和 `buildRuntimeContext()`：历史仅含固定用户/助手消息，本轮动态背景放在当前用户消息之后；下轮不重放这条旧背景。

**完整保留方案**在同样的用户/助手历史中，保留每轮原始动态 system 背景，并继续追加新的背景。因此旧请求的输入部分更接近下一次请求的连续前缀，但背景会逐轮叠加。

示例中，当前方案第六轮只携带第六轮的当前背景；完整保留方案携带第一至第六轮全部背景。缓存相同内容仍占上下文窗口，不因缓存命中从输入长度中消失。

## 实验方法

- 使用真实 `deepseek-flash` 的 Responses API，共 24 个请求，分为两组，每种方案每组 6 轮。
- 第一组顺序为当前方案再完整保留；第二组反过来，降低先后顺序影响。每个组/方案带独立实验标记，但无法要求服务端清空缓存，不能称为严格冷缓存实验。
- 使用当时加载的实际系统提示词、真实工具声明和项目上下文组装函数。测试禁止调用工具，关闭 thinking，单次输出上限 96 Token，实际没有执行任何文件或命令操作。
- 固定的合成历史、固定资料、分钟变化的时钟，以及目录和执行权限变化。每轮要求返回当前目录与是否允许执行命令的 JSON。
- 两种方案的历史助手文本均使用同一固定文本，避免生成结果差异改变后续输入。因此这里比较的是受控请求结构，不是完整真实任务中所有模型输出的缓存复用。
- 请求间隔 1.5 秒。上限 24 次、200,000 输入 Token；实际累计输入 58,212，累计输出 340。没有使用用户聊天记录或图片。

脚本：[prefix-cache-comparison.mjs](experiments/prefix-cache-comparison.mjs)。结果与逐请求明细：[prefix-cache-comparison-results.json](experiments/prefix-cache-comparison-results.json)。结果保存了提示词版本、源文件摘要、预期状态、解析结果和 API usage，不包含凭据。

在项目根目录复现：

```sh
# 仅离线比较请求结构，不调用 API
node --experimental-strip-types docs/research/prefix-cache/experiments/prefix-cache-comparison.mjs

# 使用环境中的 DeepSeek 凭据进行受限真实对照，会产生 API 用量
node --env-file-if-exists=.env --experimental-strip-types docs/research/prefix-cache/experiments/prefix-cache-comparison.mjs --live
```

注意：脚本每次运行会覆盖结果 JSON；需要保留本次证据时，先复制结果或更换输出路径。离线统计使用序列化字符和项目启发式估算，只描述结构，不能当成供应商真实前缀 Token。下表全部 Token 数据来自 API usage。

## 实测结果

| 指标 | 当前方案 | 完整保留旧背景 |
| --- | ---: | ---: |
| 请求数 | 12 | 12 |
| 累计输入 Token | 22,296 | 35,916 |
| 累计缓存命中 Token | 11,776 | 26,880 |
| 累计未命中 Token | 10,520 | 9,036 |
| 加权缓存命中率 | 52.82% | 74.84% |
| 累计输出 Token | 174 | 166 |
| 首字延迟中位数 | 669.5 ms | 607.5 ms |
| 格式与当前状态校验通过 | 12/12 | 11/12 |
| 每组第六轮输入 Token | 1,986 | 4,254 |

完整保留的累计输入增加 **61.09%**，绝对未命中 Token 减少 **14.11%**；最后一轮输入约为当前方案的 **2.14 倍**。命中率升高，同时受“未命中减少”和“额外旧内容被命中”两种因素影响，不能只看百分比。

完整保留的一个请求结束状态为 completed，但未得到可解析为预期 JSON 的结果。该次未保留原始输出，不能确定具体原因，也不能归因于旧权限冲突。其余已解析的回答都通过状态检查；本实验没有证明存在权限越界或系统性的陈旧状态错误。

延迟只作描述：样本小、存在首次连接与服务端负载影响、请求输出长度略不同。两个执行顺序下的总中位数表现不同，不能承诺上线后固定提速或给出统计显著结论。

## 缓存命中更高为什么只省一点

按实验日期官方 Flash 非高峰参考费率，缓存输入、未命中输入和输出分别为每百万 Token 0.003、0.15、0.6 美元。这里只折算参考费用，不代表账户实际扣费；不同时段的绝对费用可能变化。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)

| 参考费用 | 当前方案 | 完整保留 |
| --- | ---: | ---: |
| 输入费用 | $0.001613328 | $0.001436040 |
| 加上本次实际输出 | $0.001717728 | $0.001535640 |

在该小样本中，输入费用约减少 **10.99%**，总费用约减少 **10.60%**。绝对金额很小，不能由此推算日常用户的长期节省金额。

多保留旧背景，新增了 15,104 个缓存输入 Token，换来减少 1,484 个未命中 Token。输入费用是否下降取决于缓存/未命中单价比：本例临界值约为 **9.83%**。Flash 此次采用的比值为 2%，所以略省钱；换成缓存折扣不同的模型，结果可能反过来。

因此不能把“完整保留更省”写成跨模型通用事实。输入总长度增加则不依赖缓存折扣，它会影响更长会话的压缩时机。

## 短占位回复实验的适用范围

1. 在本次固定短回复场景下，直接完整保留旧背景的成本收益有限，需要与上下文容量取舍；真实长回复复测的结果见上文。
2. 一次短实验中仍未出现足以证明的陈旧权限错误；旧背景积累是设计上的风险和负担，不应描述为已经复现的越权漏洞。
3. 图片和工具结果也占窗口，后续方案仍须控制重复背景的增长；不能只依据短回复实验决定项目优先级。
4. 后续若做版本化模型输入日志，可以让模型真实上下文可重放，并研究稳定资料保留、仅追加有作用域的状态变化、压缩时建立新边界。但不能简单把所有旧 system 消息永久保留。

缓存统计仍值得作为诊断能力补齐，但不要求用户自己观察。对照、计算和归档已自动完成，实施判断应以上文修正结论为准。

## 补充实验 会话越长是否越划算

用户提出长会话可能放大收益后，将相同方法延长为 20 轮、两种方案共 40 次真实 Flash 请求。此次顺序为完整保留后当前方案，仍固定合成历史和状态查询，未执行工具；累计输入 174,912 Token。明细见 [20 轮结果](experiments/prefix-cache-long-results.json)。

```sh
node --env-file-if-exists=.env --experimental-strip-types docs/research/prefix-cache/experiments/prefix-cache-comparison.mjs --live --long
```

该模式独立保存 long 结果，不覆盖 6 轮结果；最多 40 次请求、200,000 输入 Token。它只有一个长会话对照组，延迟与回答质量不应作统计推广。参数生成的独立实验标记会影响少量 Token，分组比较采用本次内部数据。

| 累计到第几轮 | 当前方案输入费用 | 完整保留输入费用 | 完整保留节省比例 |
| --- | ---: | ---: | ---: |
| 6 | $0.000809364 | $0.000720720 | 10.95% |
| 10 | $0.001251060 | $0.001096674 | 12.34% |
| 15 | $0.001806036 | $0.001650978 | 8.59% |
| 20 | $0.002364102 | $0.002234298 | 5.49% |

同一非高峰参考费率下，前期累计节省确实变大，但没有随会话长度持续变大：累计节省金额在第 15 轮约为 $0.000155，第 20 轮降到约 $0.000130。此处只比较输入费用，避免生成长度不同影响对照。

第 20 轮单次请求更直观：当前方案输入 2,703 Token，完整保留为 11,321 Token，约 **4.19 倍**。完整保留虽然该轮未命中更少（569 对 655），但缓存输入更多，折算该轮输入费用反而高约 **12.66%**。

20 轮累计命中率约为当前方案 65.79%、完整保留 90.40%；累计输入约为 44,361 对 130,551。高命中率同时包含大量额外的已缓存背景，不能直接解释为更高的净效率。

若每轮背景大小大致固定、从不压缩，完整保留在第 n 轮比当前方案多发送约 n−1 份背景；累计多发送背景的数量约为 n(n−1)/2。缓存降低这些输入的单价，但不会使其免费。这是该固定大小模型下的增长分析，不是对任意真实会话的精确预测。

本轮状态/JSON 校验为当前方案 20/20，完整保留 13/20；失败 7 次的已保存流式输出均只有空白。已解析的回答仍然没有发现旧目录或旧权限回答错误。该现象可能涉及模型、JSON 模式与多条 system 消息的交互，本实验不能确定原因；它不能作为“已经发生权限越界”的证据。

该补充实验只能说明：短占位回复下，永久保留背景的成本可能逐步抵消收益。它没有覆盖长 assistant 输出的复用，不能用于反驳用户提出的真实长回复收益。上文复测已经显示不同结果。

## 实验没有覆盖的情况

三次实验均未测试真实工具执行、多步推理、大量图片、长会话压缩或不同供应商。状态校验是合成字段，不是行为安全评测；没有统计功效分析。正式改变回放语义前，仍应验证任务质量和失效状态处理。

DeepSeek 缓存默认启用并按服务端已有前缀单元命中，存在构建与淘汰行为，不能保证每次命中。[官方缓存机制](https://api-docs.deepseek.com/guides/kv_cache/)
