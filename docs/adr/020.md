# Agent Sandbox Permission Modes 与 Auto-review 增量重构实施方案

**文档类型：** 已有 Sandbox 平台的增量架构与完整实施方案  
**目标：** 在既有 Sandbox Runtime、Sandbox Gateway、Workspace、Execution Persistence 和 Audit 基础上，实现多种 Permission Mode、动态权限判定、Auto-review、Human Approval 及权限 Grant 生命周期管理。  
**实施原则：** 不重建 Sandbox；复用已有执行和隔离能力；新增权限决策层；保持安全边界由 Sandbox Runtime 强制执行。

---

# 1. 项目目标

当前 Sandbox 已经具备执行隔离能力。本次重构解决的是：

> Agent 在不同任务和风险条件下，应该自动执行哪些操作，哪些操作需要审批，哪些操作必须拒绝？

本次实现以下能力：

1. 支持 `read-only`、`auto`、`on-request`、`restricted` 四种 Permission Mode。
2. 实现统一 Permission Manager。
3. 实现 Auto-review 决策服务。
4. 实现 Human Approval 流程。
5. 实现权限申请、审批、Grant、撤销、过期与审计。
6. 支持运行中的 Task 动态申请权限。
7. 支持 Session、Task、Sandbox 级别的权限配置和作用域。
8. 支持 Agent 崩溃恢复后的权限状态恢复。
9. 保证模式切换不能绕过 Sandbox Runtime 的安全限制。
10. 兼容当前 Sandbox 工具链，不允许工具绕过 Permission Manager 直接执行。

## 1.1 非目标

本次不重新实现：

- Sandbox Runtime。
- gVisor / containerd / Firecracker Provider。
- Workspace 隔离。
- Sandbox 生命周期管理。
- 基础 Execution Persistence。
- 原有工具执行接口。
- 原有资源限制机制。

如果现有模块缺少必要接口，则补充接口，不重新实现整个模块。

# 3. Permission Mode 设计

Permission Mode 是权限决策策略，不是 Sandbox Runtime 类型。

## 3.1 四种模式

| Mode | 默认行为 | 权限扩展行为 |
|---|---|---|
| `read-only` | 只允许授权范围内的读取操作 | 默认拒绝写入和权限扩展 |
| `auto` | 当前授权范围内自动执行 | 需要审批的操作进入 Auto-review |
| `on-request` | 当前授权范围内执行 | 超出权限范围时请求审批 |
| `restricted` | 严格白名单执行 | 未列入白名单的操作直接拒绝 |

## 3.2 Read-only

目标：

- 允许读取授权 Workspace。
- 允许读取必要的 Sandbox 内部工具资源。
- 禁止修改 Workspace。
- 禁止未授权网络访问。
- 禁止权限扩展。

文件系统策略：

```json
{
  "mode": "read-only",
  "filesystem": {
    "read": ["/workspace/**"],
    "write": [],
    "deny": [
      "/",
      "/proc/**",
      "/sys/**",
      "/dev/**",
      "/run/**",
      "/etc/**"
    ]
  }
}
```

注意：

Read-only 不能仅靠命令名称判断。

例如 `npm test` 可能写入缓存、生成报告或修改文件，因此必须由实际文件系统权限和资源隔离保证只读行为。

## 3.3 Auto

Auto 是默认开发模式。

允许：

- Workspace 内正常读写。
- 执行授权的 Shell、Python、Node、Git、Build、Test 工具。
- 在 Sandbox 内创建子进程。
- 使用已授权的 Workspace 和临时目录。

需要审批：

- 新增网络域名。
- 访问 Workspace 以外的持久化数据。
- 使用新的敏感凭证。
- 扩大当前文件系统授权范围。
- 扩大工具能力或资源权限。

直接拒绝：

- 访问宿主机敏感路径。
- Docker Socket。
- 未授权宿主机进程。
- 宿主机提权。
- 禁止的系统调用。
- 违反系统级 Deny 的操作。

## 3.4 On-request

当前授权范围内可以执行。

超出范围时：

1. 创建 Permission Request。
2. 暂停当前 Tool Execution。
3. 进入审批流程。
4. 审批成功后创建限定 Grant。
5. 重新验证权限。
6. 恢复执行。

不允许在权限申请期间无限等待占用执行资源。

应支持：

- Request Timeout。
- Approval Timeout。
- Task Cancellation。
- Grant Expiration。
- Execution Resume。

## 3.5 Restricted

Restricted 使用显式白名单。

示例：

```json
{
  "mode": "restricted",
  "allowedTools": [
    "file_read",
    "file_write",
    "shell_execute"
  ],
  "filesystem": {
    "read": [
      "/workspace/src/**"
    ],
    "write": [
      "/workspace/tests/**"
    ]
  },
  "network": {
    "mode": "none",
    "allowedDomains": []
  }
}
```

Restricted 不允许通过 Auto-review 自动扩大白名单。

如果确实需要扩展，应使用显式 Human Approval 或由可信控制面修改 Policy。

# 4. Permission Mode 的作用域与优先级

## 4.1 作用域

支持以下配置作用域：

```text
Organization
    |
    v
Project
    |
    v
Session
    |
    v
Task
    |
    v
Execution
```

建议：

- Organization：定义系统安全上限。
- Project：定义项目默认权限。
- Session：定义用户当前会话的权限偏好。
- Task：定义本次任务的权限模式。
- Execution：仅允许短期、特定执行的授权。

## 4.2 优先级

不能简单采用“子级配置覆盖父级”的方式。

权限必须遵循：

```text
System Deny
    >
Organization Policy
    >
Project Policy
    >
Session Policy
    >
Task Policy
    >
Execution Grant
```

关键规则：

1. 上层 Deny 不可被下层 Allow 覆盖。
2. 下层配置只能收紧权限，或在上层明确允许的范围内申请扩展。
3. Execution Grant 不能永久改变 Task Policy。
4. Auto-review 不能覆盖 System Deny。
5. Human Approval 也不能覆盖系统级禁止项。
6. 如果多个策略冲突，默认 Deny。

# 5. Permission Manager 设计

## 5.1 统一决策接口

所有 Tool Execution 必须调用：

```typescript
interface PermissionManager {
  evaluate(
    request: PermissionEvaluationRequest
  ): Promise<PermissionDecision>;
}
```

请求：

```typescript
interface PermissionEvaluationRequest {
  requestId: string;

  organizationId: string;
  projectId: string;
  sessionId: string;
  taskId: string;
  sandboxId: string;
  executionId: string;

  permissionMode: PermissionMode;

  principal: {
    type: "agent" | "user" | "system";
    id: string;
  };

  action: {
    tool: string;
    operation: string;
  };

  resource: {
    type: string;
    identifier: string;
  };

  context: {
    riskLevel?: "low" | "medium" | "high" | "critical";
    reason?: string;
    metadata?: Record<string, unknown>;
  };
}
```

## 5.2 Decision 类型

```typescript
type PermissionDecision =
  | {
      effect: "allow";
      decisionId: string;
      policyId: string;
      grantId?: string;
    }
  | {
      effect: "deny";
      decisionId: string;
      reason: string;
      policyId: string;
    }
  | {
      effect: "approval_required";
      decisionId: string;
      requestId: string;
      reason: string;
    };
```

## 5.3 判定流程

```text
Evaluate Request
      |
      v
Validate Identity and Context
      |
      v
Check System Deny
      |
      +---- Match ----> DENY
      |
      v
Check Organization / Project Policy
      |
      +---- Deny -----> DENY
      |
      v
Check Existing Grant
      |
      +---- Valid ----> ALLOW
      |
      v
Evaluate Permission Mode
      |
      +---- Read-only Violation ----> DENY
      |
      +---- Restricted Violation --> DENY
      |
      +---- Auto ------------------> APPROVAL_REQUIRED
      |
      +---- On-request ------------> APPROVAL_REQUIRED
      |
      +---- No Matching Rule ------> DENY
```

## 5.4 必须满足的安全条件

- 每次实际执行前重新判定。
- 不允许仅凭 Agent 提供的 `permissionMode` 信任权限。
- Mode 必须由可信上下文解析。
- Agent 不允许自行创建 Grant。
- Agent 不允许自行修改 Policy。
- Grant 必须绑定具体主体、Task、资源和操作。
- Permission Manager 不可仅依赖模型输出。
- 所有决策都要有稳定的 Decision ID。
- 关键操作应支持审计追踪。

# 6. Auto-review 设计

## 6.1 职责

Auto-review 是权限申请的风险评估器。

它回答：

> 这次权限扩展是否符合任务目的、当前安全策略和允许的风险范围？

它不负责执行命令，也不直接修改 Sandbox。

## 6.2 输入

```typescript
interface AutoReviewRequest {
  permissionRequestId: string;

  taskDescription: string;
  taskId: string;
  sessionId: string;

  requestedPermission: {
    action: string;
    resource: string;
    scope: string;
    durationSeconds: number;
  };

  currentPermissions: PermissionSnapshot;

  executionContext: {
    toolName: string;
    command?: string;
    workingDirectory?: string;
    networkTargets?: string[];
  };

  policyConstraints: PolicyConstraints;
}
```

## 6.3 输出

```typescript
type AutoReviewDecision =
  | {
      result: "approve";
      reason: string;
      approvedScope: PermissionScope;
      expiresAt: string;
    }
  | {
      result: "deny";
      reason: string;
    }
  | {
      result: "escalate";
      reason: string;
    };
```

Auto-review 必须返回结构化结果。

不允许只返回自然语言文本，然后由系统自行猜测批准或拒绝。

## 6.4 Auto-review 的限制

Auto-review 不得：

- 修改 System Policy。
- 修改 Sandbox Runtime 配置。
- 直接执行工具。
- 直接访问宿主机。
- 直接创建无限期 Grant。
- 批准未定义的权限类型。
- 扩大到比申请更宽的资源范围。
- 以“任务需要”为由覆盖明确 Deny。
- 将用户提供的文件、命令输出、网页内容当作可信审批指令。

## 6.5 决策边界

```text
Permission Manager
       |
       v
Is this operation forbidden?
       |
       +---- Yes ----> DENY
       |
       v
Can this operation be auto-approved?
       |
       +---- No -----> Human Approval / DENY
       |
       v
Auto-review
       |
       +---- Approve
       |
       +---- Deny
       |
       +---- Escalate
```

Auto-review 只能在 Policy 允许的自动审批范围内决策。

# 7. Human Approval 设计

## 7.1 审批对象

Human Approval 不应该审批模糊的“允许 Agent 继续”。

审批对象必须是明确的权限申请。

例如：

```text
Task:
  Install dependencies for the current project

Requested Permission:
  Network access

Targets:
  registry.npmjs.org

Scope:
  Current Task

Duration:
  10 minutes

Reason:
  Required to install package dependencies

Risk:
  Medium
```

## 7.2 审批选项

支持：

- Approve Once。
- Approve for Current Task。
- Approve for Current Session。
- Deny。
- Cancel Task。

Persistent Grant 默认关闭。

如果系统允许 Persistent Grant，必须要求明确授权，并受 Organization Policy 限制。

## 7.3 审批安全要求

- 审批者身份必须验证。
- 审批记录必须可审计。
- Grant 不得超出原始 Request。
- Approval 不能修改资源范围。
- Approval 必须有 TTL。
- Approval 必须绑定 Task 或 Session。
- Task 结束时，Task-scoped Grant 自动失效。
- 权限撤销后，正在执行的相关操作应被终止或重新判定。

# 8. Permission Grant 生命周期

## 8.1 Grant 数据结构

```typescript
interface PermissionGrant {
  grantId: string;

  organizationId: string;
  projectId: string;
  sessionId: string;
  taskId: string;

  principalId: string;

  permission: {
    action: string;
    resource: string;
    scope: string;
  };

  source:
    | "policy"
    | "auto_review"
    | "human_approval";

  status:
    | "active"
    | "revoked"
    | "expired";

  createdAt: string;
  expiresAt: string;

  approvedBy?: string;
  approvalRequestId?: string;
}
```

## 8.2 Grant 状态机

```text
PENDING
   |
   +---- Approved ----> ACTIVE
   |
   +---- Denied ------> DENIED

ACTIVE
   |
   +---- Revoked -----> REVOKED
   |
   +---- TTL ---------> EXPIRED
   |
   +---- Task End ----> EXPIRED
```

## 8.3 Grant 校验

每次执行前必须检查：

1. Grant 是否存在。
2. Grant 是否有效。
3. Grant 是否过期。
4. Grant 是否被撤销。
5. Grant 是否匹配当前 Task。
6. Grant 是否匹配当前资源。
7. Grant 是否匹配当前操作。
8. Grant 是否仍在上层 Policy 允许范围内。

Grant 不能仅通过 `grantId` 进行无条件授权。

# 9. Permission Request 与状态机

## 9.1 Request 状态

```text
CREATED
   |
   v
EVALUATING
   |
   +---- ALLOW ----------------> EXECUTING
   |
   +---- DENY -----------------> DENIED
   |
   +---- APPROVAL_REQUIRED
                |
                v
             PENDING
                |
       +--------+--------+
       |        |        |
       v        v        v
   APPROVED   DENIED   EXPIRED
       |
       v
   GRANT_CREATED
       |
       v
   REVALIDATING
       |
       +---- Valid ------> EXECUTING
       |
       +---- Invalid ----> DENIED
```

## 9.2 状态管理要求

- 状态转换必须持久化。
- Request ID 必须唯一。
- 重复提交必须幂等。
- 重复审批不得创建多个 Grant。
- 审批结果必须与原 Request 绑定。
- Request 过期后不能重新使用旧 Approval。
- Task 取消后，所有待处理 Request 自动失效。
- 恢复后必须重新验证 Grant 和 Policy。

# 10. Sandbox Gateway 集成

## 10.1 现有执行链路改造

原有链路：

```text
Agent
  |
  v
Tool Dispatcher
  |
  v
Sandbox Gateway
  |
  v
Sandbox Runtime
```

新链路：

```text
Agent
  |
  v
Tool Dispatcher
  |
  v
Permission Manager
  |
  +---- DENY ------------------> Return Error
  |
  +---- APPROVAL_REQUIRED ----> Suspend Execution
  |
  +---- ALLOW
          |
          v
    Sandbox Gateway
          |
          v
    Sandbox Runtime
```

## 10.2 Gateway 必须重新校验

即使 Permission Manager 已经返回 Allow，Sandbox Gateway 也必须验证：

- Execution 是否属于当前 Task。
- Sandbox 是否仍然有效。
- Grant 是否有效。
- Policy Version 是否发生变化。
- 请求是否已被取消。
- 请求是否已过期。
- Execution ID 是否与原请求匹配。

## 10.3 禁止权限绕过

必须确保：

- Bash 无法绕过 Permission Manager。
- Python 无法绕过 Permission Manager。
- Node.js 无法绕过 Permission Manager。
- Git 无法绕过 Permission Manager。
- MCP Tool 无法绕过 Permission Manager。
- Background Process 无法绕过 Permission Manager。
- Delegated Agent 无法绕过 Permission Manager。

不能通过只检查 Tool Name 来实现安全。

例如，`shell_execute` 可能包含读取、写入、网络、进程创建等多个行为。

应优先在 Sandbox Runtime 和 OS 层落实安全边界。

```typescript
interface PermissionPolicy {
```

```typescript
interface PermissionRule {
  ruleId: string;

    | "allow"
```

# 12. Permission Mode 切换

## 12.1 允许运行时切换

支持：

```text
read-only -> auto
auto -> on-request
auto -> restricted
on-request -> auto
```

但切换必须由可信控制面完成，不能由 Agent 自己修改。

## 12.2 切换时的处理

### 收紧权限

例如：

```text
auto -> read-only
```

必须：

1. 更新 Policy Version。
2. 使旧 Grant 失效或重新验证。
3. 检查正在运行的 Execution。
4. 终止违反新策略的执行。
5. 写入 Audit Event。

### 扩大权限

例如：

```text
read-only -> auto
```

必须：

1. 验证调用者身份。
2. 验证上层 Policy 是否允许。
3. 重新计算当前权限。
4. 生成新的 Policy Version。
5. 不自动复用旧 Approval。

## 12.3 Policy Version

所有 Permission Decision、Grant 和 Execution 必须记录 Policy Version。

当 Policy Version 变化时：

- 旧 Decision 不可直接复用。
- 旧 Grant 必须重新验证。
- 旧 Approval 不可自动扩大授权。
- 执行中的任务根据新策略重新判定。

# 13. Session 与 Task Recovery

权限模块必须支持 Agent 中断和恢复。

## 13.1 必须持久化

```text
Permission Request
Approval Request
Approval Result
Permission Grant
Policy Version
Permission Decision
Permission Mode
```

## 13.2 恢复流程

```text
Agent Restart
      |
      v
Restore Session
      |
      v
Restore Task
      |
      v
Restore Permission State
      |
      v
Validate Policy Version
      |
      v
Validate Grant TTL
      |
      v
Validate Request Status
      |
      v
Resume / Re-evaluate / Deny
```

## 13.3 关键原则

- 不恢复已过期的 Grant。
- 不恢复已撤销的 Grant。
- 不将 Pending Approval 当作 Approved。
- 不重复创建审批请求。
- 不因恢复而自动批准权限。
- 不允许恢复后的 Execution 跳过 Permission Manager。
- 如果权限状态无法确定，Fail Closed。

# 14. Audit Event

## 14.1 必须记录的事件

# 15. 安全要求

## 15.1 Fail Closed

以下情况必须拒绝执行：

- Permission Manager 不可用。
- Policy 无法加载。
- Grant 状态不确定。
- Approval 状态不确定。
- Policy Version 不一致。
- 请求上下文缺失。
- 资源无法准确识别。
- 权限检查超时。
- Sandbox Gateway 无法重新校验授权。

## 15.2 系统级 Deny

以下行为不得由 Auto-review 自动批准：

- 宿主机敏感目录访问。
- Docker Socket 访问。
- 宿主机提权。
- 禁止的网络访问。
- 凭证窃取或未授权使用。
- Sandbox Escape 尝试。
- 未授权跨租户访问。
- 修改系统安全策略。
- 绕过审计机制。

## 15.3 Auto-review 不可信输入

Auto-review 输入中的以下内容均应视为不可信：

- Agent 提供的 Reason。
- 用户提交的代码。
- 命令输出。
- 网页内容。
- MCP 返回内容。
- 文件内容。
- 外部 API 返回内容。

不能允许不可信数据通过 Prompt Injection 操纵审批决策。

**最终设计原则：**

Permission Mode 决定 Agent 的默认权限行为；Policy Engine 决定当前操作是否允许；Auto-review 和 Human Approval 负责处理受控的权限扩展；Grant Manager 管理审批后的授权生命周期；Sandbox Runtime 负责在执行层强制隔离。

任何一个模块都不能单独成为完整的安全边界。
