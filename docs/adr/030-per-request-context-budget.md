# ADR 030 — 每次模型请求前的上下文预算

**状态：** 已接受
**日期：** 2026-11-08
**相关：** ADR 004（上下文检索）、ADR 014（agent loop）、ADR 016（SQLite）、
ADR 029（结束原因）

---

## 1. 决策

在**每一次**模型请求之前，按该模型的实际窗口重新计算预算，而不是只在回合开始前算一次。

```
窗口 − 输出预留 − 安全余量 − (系统提示词 + 工具描述) = 可用预算
```

超出时按固定顺序处理：

1. **压缩较早的工具结果**（保留开头 + 说明压缩了多少），调用与结果成对保留；
2. **丢弃当前用户消息之前的历史**，工具调用与其结果**成对**删除；
3. 仍然放不下 → 结束本轮，`finish_reason = budget_exhausted`，保留已有半成品与一句说明。

当前回合本身（最后一条用户消息之后的所有内容）**不丢弃**：它是进行中的工作。

## 2. 背景

`SessionService.prepare()` 已经在回合开始前处理历史预算与压缩，但它看不到进入循环之后
发生的事情：模型输出、工具调用、工具结果不断追加。

```
历史已接近窗口上限 → 读几个大文件 → 工具输出继续追加 → 下一次请求超过模型窗口
```

原有控制是三个固定字符上限：单次输出上限、单轮工具字符上限（240k）、步数上限。
它们不构成预算：

- 240k 字符对不同模型意味着不同的 token 数（DeepSeek 128k/1M 窗口差异很大）；
- 没有把系统提示词、工具 schema、推理记录算进去；
- 一个读到 200 KB 文件的回合可以在第 2 步就超过窗口。

## 3. 预算的组成

| 项 | 来源 | 是否可裁剪 |
|---|---|---|
| `windowTokens` | 模型 profile | 否 |
| `outputReserveTokens` | `maxOutputTokens` | 否 |
| `safetyBufferTokens` | profile 的安全余量 | 否 |
| 系统提示词 | `buildInstructions()` | 否（稳定前缀，改它会破坏缓存） |
| 工具描述 | `ToolRegistry.schemas()` | 否（工具是能力声明） |
| 历史消息 | 会话回放 | **可丢**（最旧优先） |
| 工具调用/结果 | 本轮循环 | **可压缩；成对才可丢** |
| 推理记录 | 模型返回 | 可丢（与调用同组） |

估算复用 `session/tokens.ts` 的 `mixed` 估算器（CJK 1 字符 ≈ 1 token，其余 4 字符 ≈ 1），
刻意偏保守：早压缩的代价是一次摘要调用，晚压缩的代价是一整轮请求被拒绝。

## 4. 处理顺序与不变量

1. **先保留、再压缩、最后丢弃。** 输出预留与安全余量在预算之前扣掉，避免"预算算得刚刚好、
   实际输出把窗口撑破"。
2. **成组处理。** `function_call` 与 `function_call_result` 靠 `callId` 配对；只删一半会产生
   一个 provider 无法解析的请求。所以删除的入口永远是调用，结果是它的附属；找不到结果的
   孤立调用不删，交给"预算耗尽"处理。
3. **最新的工具结果不压缩。** 它是模型刚拿到的、要据此决策的内容。
4. **当前回合不丢弃。** 保护范围从最后一条用户消息开始；保护区内只允许压缩，不允许删除。
5. **耗尽要明说。** 发一个注定被拒绝的请求比提前结束更糟：用户已经等了，却只拿到一个
   400。结束时保留半成品并给出一句可执行的建议。

## 5. 代码位置

- `src/agent/context-budget.ts`：`estimateSystemTokens` / `estimateItemTokens` / `fitContext`；
- `src/agent/loop.ts`：每一步调用 `fitContext`，用裁剪后的输入发起请求；耗尽时以
  `budget_exhausted` 结束；
- `src/service/chat.ts`：从会话绑定的模型 profile 构造 `ContextBudget`，经 `AgentOptions`
  传入；
- `completed` 事件带 `steps` 与 `contextTokens`，回合记录同时写入 `context_tokens`。

## 6. 与既有压缩的关系

两者是两层，不互相替代：

| 层 | 触发点 | 处理对象 | 手段 |
|---|---|---|---|
| 会话层 `prepare()` | 回合开始 | 历史 | 滚动摘要 + 尾部截断 |
| 循环层 `fitContext()` | 每次请求 | 本轮工作 + 历史兜底 | 压缩工具结果 + 丢弃旧历史 |

会话层的摘要**不会**破坏工具调用与结果的对应关系：历史上只有用户/助手文本，工具事件只
存在于本轮的 `input` 与 `turn_events` 中（ADR 028）。因此"压缩时如何不破坏配对"这个问题
只在循环层出现，由第 4 节的成组规则回答。

## 7. 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只靠单轮工具字符上限 | 字符不等于 token，且不含提示词/工具/推理 |
| 只在回合开始预算 | 循环内的追加正是超限的来源 |
| 超限时直接报错 | 已经产生的工作被丢弃，用户只得到一个 400 |
| 丢弃最新的工具结果 | 模型刚拿到的依据被抽走，下一步必然重复调用 |
| 单独丢弃一个 function_call | 请求不再成对，provider 拒绝或模型混淆 |
| 每次请求全量重新摘要 | 摘要调用昂贵且慢，工具结果是更直接的裁剪对象 |

## 8. 测试

- **context-budget**：放得下时原样返回；压缩最旧结果、保留调用、不压缩最新结果；
  丢弃旧历史时成对删除且保留当前回合；孤立调用不单独删除；保护区放不下 → `exhausted`；
  系统提示词与工具 schema 计入预算；四种输入项的估算。
- **loop**：并行两个结果时压缩较旧的一个，第二次请求仍在预算内并完成；
  单个大结果无法压缩时以 `budget_exhausted` 结束，保留部分文本，且第二次模型调用**没有发生**。

## 9. 后果与边界

- **预算是估算，不是精确计数。** 安全余量与保守估算负责吸收误差；最终仍由 provider 决定。
  真正的精确计数需要在请求后回填 usage，并据此调整下一步预算，属于后续工作。
- **压缩会丢失细节。** 被压缩的结果保留开头与原始长度，模型可以看到"这里曾经有更多"，
  但无法据此还原内容；需要时它会重新读取。
- **丢弃历史是兜底，不是首选。** 正常路径应由会话层摘要处理历史；循环层丢弃只在
  "历史本来就快满了、这一轮又产生了很多工具输出"时发生。
- **耗尽不是失败。** `budget_exhausted` 与 `loop_exhausted` 一样属于正常结束，用户可以说
  "继续"或把任务拆小；统计上不应计入失败率。
