# Agent Sandbox 完整重构实施方案

## 1. 项目目标

### 1.1 项目名称

Agent Sandbox Execution Platform

### 1.2 重构目标

将现有 Agent 的工具执行体系重构为统一的 Sandbox 执行平台，为 Agent 提供隔离、安全、可审计、可恢复的执行环境。

重构完成后，Agent 可以在 Sandbox 中执行：

- Shell 命令
- Python、Node.js 等脚本
- Git 操作
- 项目依赖安装
- 代码编译和测试
- 文件读取、修改和生成
- 受控的外部网络请求
- 其他经授权的工具操作

但 Agent 不应直接获得宿主机权限，也不应通过子进程、脚本、符号链接、环境变量或其他间接方式绕过 Sandbox 的权限边界。

### 1.3 核心验收目标

重构必须同时满足以下要求：

1. 所有不可信代码都在隔离环境中执行。
2. Agent 无法直接访问宿主机文件系统。
3. Agent 无法直接管理宿主机容器运行时。
4. 不同 Task 之间相互隔离。
5. 文件系统、网络和进程资源均有明确限制。
6. 所有执行行为可审计。
7. Agent Session 崩溃后可以恢复。
8. Sandbox 崩溃后可以重建执行环境。
9. 未知执行结果不会被错误认定为成功或失败。
10. 旧工具执行路径不能绕过新的 Sandbox。

本次重构不以“成功创建容器”为完成标准，而以完整的安全边界和任务执行链路为完成标准。

```text
                     |

                     |
                     v
             Sandbox Controller
                     |
```

## 2.1 组件职责

### Agent Runtime

负责：

- 理解用户需求。
- 规划任务。
- 选择工具。
- 生成命令。
- 处理执行结果。
- 根据结果继续下一步操作。

不负责：

- 创建宿主机容器。
- 修改 Sandbox 权限。
- 访问 containerd Socket。
- 直接操作宿主机文件。
- 自行决定扩大 Sandbox 权限。

### Tool Dispatcher

统一接收 Agent 的工具调用。

所有本地代码执行操作必须经过此组件。

负责：

- 工具参数校验。
- 工具类型路由。
- Task 和 Sandbox 绑定。
- 调用 Permission Manager。
- 调用 Sandbox Gateway。
- 将结果返回 Agent。

不得保留绕过 Sandbox 的本地 Shell 执行路径。

### Permission Manager

负责：

- 读取当前 Task 的权限策略。
- 检查文件读写范围。
- 检查网络访问权限。
- 检查工具调用权限。
- 判断是否需要审批。
- 拒绝超出最大授权边界的操作。

Permission Manager 是策略决策层，不是最终执行隔离层。

### Sandbox Gateway

所有 Sandbox 执行请求的唯一入口。

负责：

- 校验 Sandbox ID。
- 校验 Task 归属。
- 校验执行请求。
- 生成 Execution ID。
- 执行幂等性检查。
- 记录执行事件。
- 将命令交给 Sandbox Controller。
- 返回执行结果。

Agent 不得直接调用 Runtime Manager。

### Sandbox Controller

负责：

- 创建 Sandbox。
- 启动 Sandbox。
- 停止 Sandbox。
- 检查 Sandbox 状态。
- 重新创建 Sandbox。
- 清理过期 Sandbox。
- 监控容器运行状态。

Controller 不允许接收 Agent 提供的任意 OCI 配置、挂载参数或运行时参数。

### Runtime Manager

负责对接 containerd 和 gVisor。

只允许使用经过审核的固定配置模板。

负责：

- 创建容器。
- 绑定工作区。
- 设置资源限制。
- 配置 Linux 安全策略。
- 启动进程。
- 获取容器状态。
- 停止和销毁容器。

Runtime Manager 是唯一允许访问 containerd 管理接口的业务组件。

# 3. Sandbox Runtime 实现

## 3.1 技术选型

第一版目标技术：

| 模块 | 技术 |
|---|---|
| Container Manager | containerd |
| Isolation Runtime | gVisor runsc |
| Container Interface | OCI |
| Filesystem Isolation | Mount Namespace + 独立 Workspace Mount |
| Process Isolation | PID Namespace |
| Network Isolation | Network Namespace |
| Resource Control | cgroups v2 |
| System Call Filtering | seccomp |
| Mandatory Access Control | AppArmor |
| User Isolation | User Namespace / 非 root 用户 |
| Image Management | OCI Image |
| Runtime Management | Sandbox Controller |

必须支持配置化 Runtime Provider，但第一版只实现 gVisor Provider。

建议定义：

```typescript
interface SandboxRuntime {
  create(config: SandboxConfig): Promise<SandboxHandle>;

  start(handle: SandboxHandle): Promise<void>;

  execute(
    handle: SandboxHandle,
    request: ExecutionRequest
  ): Promise<ExecutionResult>;

  inspect(handle: SandboxHandle): Promise<SandboxStatus>;

  interrupt(handle: SandboxHandle): Promise<void>;

  destroy(handle: SandboxHandle): Promise<void>;
}
```

不要将 Agent 的业务逻辑绑定到 containerd 或 gVisor 的具体实现。

## 3.2 Runtime 安全基线

每个 Sandbox 必须满足：

| 配置 | 要求 |
|---|---|
| Root User | 禁止 |
| Privileged Container | 禁止 |
| Host PID | 禁止 |
| Host Network | 禁止 |
| Host IPC | 禁止 |
| Docker Socket | 禁止 |
| containerd Socket | 禁止 |
| Host Root Mount | 禁止 |
| Arbitrary Mount | 禁止 |
| Linux Capabilities | 默认全部 Drop |
| No New Privileges | 开启 |
| Read-only Root FS | 开启 |
| Writable Workspace | 单独挂载 |
| Temporary Filesystem | 单独配置 |
| Resource Limits | 必须 |
| Execution Timeout | 必须 |
| Seccomp | 必须 |
| AppArmor | 必须 |

不得允许 Agent 自己传递以下参数：

- `--privileged`
- `--network=host`
- `--pid=host`
- `--volume=/`
- 任意宿主机挂载目录
- 任意 Runtime Binary
- 任意 OCI Runtime Configuration

所有容器配置由 Controller 生成。

## 3.3 容器镜像

维护受信任的 Sandbox Base Image。

例如：

```text
sandbox-base:python
sandbox-base:node
sandbox-base:golang
sandbox-base:general
```

镜像必须：

- 使用固定版本。
- 使用不可变 Digest。
- 禁止 Agent 修改基础镜像。
- 禁止直接使用不受信任的镜像。
- 定期扫描依赖漏洞。
- 记录镜像来源和构建记录。

Task 创建 Sandbox 时必须绑定镜像 Digest。

恢复时不能自动拉取一个未经验证的新版本镜像。

## 3.4 Workspace 挂载

Sandbox 只能访问当前 Task 授权的 Workspace。

示例：

```text
Host Workspace Storage
|
+-- task-001/
|   +-- src/
|   +-- tests/
|   +-- package.json
|
+-- task-002/
|   +-- src/
|   +-- tests/
|
+-- task-003/
    +-- src/
```

容器内部统一挂载：

```text
/workspace
```

必须保证：

1. Workspace ID 与 Task ID 有明确绑定。
2. 不允许 Agent 指定宿主机绝对路径。
3. 不允许任意增加 Mount。
4. 不允许访问其他 Task 的 Workspace。
5. 不允许通过符号链接逃逸。
6. 不允许通过 `..` 路径穿越访问宿主机目录。
7. 对文件操作进行规范化和边界检查。
8. Workspace 的读写权限由 Policy 决定。

路径检查必须结合真实文件系统语义，不能只通过字符串前缀判断。

例如不能认为：

```text
/workspace/../etc/passwd
```

因为字符串以 `/workspace` 开头就属于授权路径。

还需要处理：

- Symlink
- Hardlink
- Bind Mount
- TOCTOU
- 文件替换竞态
- 特殊文件
- 设备文件

优先通过隔离的 Mount Namespace 和安全文件操作接口限制访问。

# 4. Permission Manager

## 4.1 权限模型

采用三种决策：

```text
ALLOW
APPROVAL_REQUIRED
DENY
```

含义：

### ALLOW

符合当前 Task 的授权策略，可以直接执行。

### APPROVAL_REQUIRED

需要额外审批。

审批通过后只能在系统允许的最大权限范围内执行。

### DENY

当前操作明确禁止。

即使 Auto-review 批准，也不得突破系统级禁止策略。

## 4.2 权限策略结构

建议定义统一策略对象：

```typescript
interface SandboxPolicy {
  policyVersion: string;

  filesystem: {
    read: string[];
    write: string[];
    deny: string[];
  };

  network: {
    mode: "none" | "proxy_only";
    allowedDomains: string[];
    allowedPorts: number[];
  };

  process: {
    maxProcesses: number;
    allowShell: boolean;
  };

  resources: {
    cpuQuota: number;
    memoryLimitMB: number;
    diskLimitMB: number;
    executionTimeoutMs: number;
  };

  tools: {
    allowedTools: string[];
    deniedTools: string[];
  };
}
```

这是业务策略对象，不是直接交给容器运行时执行的 OCI 配置。

Controller 必须将策略编译为具体的 Runtime Configuration。

## 4.3 策略优先级

必须遵循：

```text
System Deny
    |
    v
Tenant Policy
    |
    v
Task Policy
    |
    v
Approval Grant
    |
    v
Runtime Enforcement
```

最终有效权限不得超过各层允许范围的交集。

审批不能覆盖 System Deny。

## 4.4 Approval Grant

审批记录必须具有明确范围：

```typescript
interface ApprovalGrant {
  approvalId: string;
  taskId: string;

  action: string;

  resourceScope: string[];

  expiresAt: string;

  approvedBy: string;

  policyVersion: string;
}
```

不能只保存：

```json
{
  "approved": true
}
```

必须记录批准的具体操作、资源范围、有效期和策略版本。

# 5. 网络隔离

## 5.1 默认网络策略

默认情况下：

```text
Sandbox -> Internet: DENY
Sandbox -> Host: DENY
Sandbox -> Private Network: DENY
Sandbox -> Metadata Service: DENY
```

如需联网，必须通过 Egress Proxy。

## 5.2 Egress Proxy

架构：

```text
Sandbox
   |
   v
Egress Proxy
   |
   v
Policy Check
   |
   +-- Domain Allowlist
   |
   +-- IP Range Check
   |
   +-- Port Check
   |
   +-- DNS Rebinding Protection
   |
   +-- Request Audit
   |
   v
External Network
```

必须：

- 默认拒绝未授权域名。
- 解析域名后检查最终 IP。
- 阻止访问 Loopback。
- 阻止访问 RFC1918 私有地址。
- 阻止访问 Link-local 地址。
- 阻止云 Metadata 地址。
- 阻止访问宿主机管理端口。
- 限制连接数和带宽。
- 记录请求目的地和结果。

不能仅依赖域名白名单。

必须防范：

- DNS Rebinding
- IP Literal
- IPv6 绕过
- 重定向绕过
- 代理绕过
- 非 HTTP 协议的直接出站连接

网络策略应由 Network Namespace 和宿主机网络层共同实施。

Sandbox 不得拥有能够自行修改网络策略的权限。

# 6. Credential Broker

禁止将宿主机长期凭证直接注入 Sandbox。

新增 Credential Broker。

职责：

1. 验证 Task 是否具有对应凭证使用权限。
2. 申请短期凭证。
3. 限制凭证访问资源。
4. 限制凭证有效时间。
5. 支持凭证撤销。
6. 对凭证使用行为进行审计。
7. 对日志进行敏感信息脱敏。

推荐架构：

```text
Agent
  |
  v
Credential Request
  |
  v
Permission Manager
  |
  v
Credential Broker
  |
  v
Short-lived Credential
  |
  v
Controlled API / Proxy
```

不得默认向容器注入：

- SSH Private Key
- Cloud Root Credentials
- Production Database Password
- Long-lived Git Token
- 宿主机环境变量中的所有密钥

如果某个工具必须使用凭证，应优先通过独立代理执行对应 API 操作。

# 7. Sandbox Gateway API

必须提供统一的 Sandbox API。

```typescript
interface SandboxService {
  create(input: CreateSandboxInput): Promise<Sandbox>;

  execute(input: ExecuteInput): Promise<ExecutionResult>;

  inspect(sandboxId: string): Promise<SandboxStatus>;

  interrupt(
    sandboxId: string,
    executionId: string
  ): Promise<void>;

  recover(sandboxId: string): Promise<Sandbox>;

  destroy(sandboxId: string): Promise<void>;
}
```

## 7.1 CreateSandboxInput

```typescript
interface CreateSandboxInput {
  taskId: string;
  workspaceId: string;

  imageDigest: string;

  policyVersion: string;

  resourceProfile: string;
}
```

Agent 不能传入任意宿主机路径或容器 Runtime 配置。

## 7.2 ExecuteInput

```typescript
interface ExecuteInput {
  sandboxId: string;

  executionId: string;

  idempotencyKey: string;

  command: string[];

  cwd: string;

  timeoutMs: number;
}
```

建议默认使用 argv 数组执行命令，避免不必要的 Shell 字符串拼接。

对于确实需要 Shell 的 Agent 场景，可以提供单独的 Shell Execution 模式，但必须在 Sandbox 内执行，不能因此绕过任何隔离策略。

## 7.3 ExecutionResult

```typescript
interface ExecutionResult {
  executionId: string;

  status:
    | "SUCCEEDED"
    | "FAILED"
    | "TIMEOUT"
    | "CANCELLED"
    | "UNKNOWN";

  exitCode?: number;

  stdout: string;

  stderr: string;

  startedAt: string;

  finishedAt?: string;
}
```

UNKNOWN 必须是正式状态，不能把执行结果未知的请求错误映射成 FAILED。

# 8. Execution Persistence

这是与 Agent Session Persistence 配合的核心模块。

Sandbox 负责执行隔离，Execution Persistence 负责记录每一次外部执行。

## 8.1 Execution 状态机

```text
CREATED
   |
   v
AUTHORIZED
   |
   v
SUBMITTED
   |
   v
RUNNING
   |
   +-------------------+
   |         |         |
   v         v         v
SUCCEEDED  FAILED   INTERRUPTED
                       |
                       v
                    UNKNOWN
                       |
                       v
                 RECONCILING
                   /     \
                  v       v
             SUCCEEDED  RETRYABLE
```

## 8.2 必须记录的事件

建议采用 append-only Execution Event Log：

```text
execution/created
execution/authorized
execution/submitted
execution/started
execution/stdout
execution/stderr
execution/finished
execution/failed
execution/interrupted
execution/reconciled
execution/retried
```

每个事件至少包含：

```typescript
interface ExecutionEvent {
  eventId: string;

  taskId: string;

  sandboxId: string;

  executionId: string;

  idempotencyKey: string;

  eventType: string;

  timestamp: string;

  policyVersion: string;

  payload: unknown;
}
```

事件日志需要持久化，不能只保存在 Agent 进程内存中。

## 8.3 防止重复执行

执行流程：

1. 创建 Execution ID。
2. 生成 Idempotency Key。
3. 持久化 `execution/submitted`。
4. 提交执行请求。
5. 记录开始事件。
6. 获取执行结果。
7. 持久化完成事件。
8. 返回 Agent。

需要保证：

- 相同 Idempotency Key 不重复创建逻辑执行任务。
- 同一个 Execution ID 不能被并发执行两次。
- 执行请求的状态可以恢复。
- 未知结果必须进入状态核验。
- 不能仅凭 Session Log 判断外部操作是否成功。

注意：执行命令本身不一定具有幂等性。对于 Docker Push、数据库写入、云资源创建等外部操作，必须根据外部系统的实际状态进行核验。

# 9. Workspace Persistence

Workspace 必须独立于 Sandbox 生命周期。

数据关系：

```text
Agent Session
     |
     v
Task
     |
     +------------------+
     |                  |
     v                  v
Sandbox             Workspace
     |                  |
     v                  v
Runtime             Persistent Storage
```

Sandbox 被销毁时，Workspace 不得自动删除。

## 9.1 Workspace 管理

需要支持：

- 创建 Workspace。
- 挂载 Workspace。
- 保存文件修改。
- 计算 Workspace 版本。
- 创建恢复点。
- 恢复指定版本。
- 删除 Workspace。
- 清理过期数据。

建议 Workspace 使用独立存储目录或存储卷。

## 9.2 Checkpoint

Checkpoint 应记录：

```typescript
interface WorkspaceCheckpoint {
  checkpointId: string;

  workspaceId: string;

  taskId: string;

  createdAt: string;

  sourceExecutionId?: string;

  contentDigest: string;
}
```

对于 Git 项目，可以使用 Git Commit 或独立 Worktree 作为版本恢复手段。

对于非 Git 文件，需要使用文件系统快照或版本化存储。

Checkpoint 不应仅仅是 Session Event Log 的一部分。

# 10. Sandbox Lifecycle

## 10.1 状态机

```text
CREATING
   |
   v
READY
   |
   v
RUNNING
   |
   +----------+
   |          |
   v          v
READY     INTERRUPTED
              |
              v
          RECOVERING
              |
          +---+---+
          |       |
          v       v
        READY   FAILED
          |
          v
       DESTROYED
```

另外需要支持：

- EXPIRED
- TERMINATING
- DESTROYED

所有状态迁移必须经过 Controller。

## 10.2 Heartbeat

Controller 定期检查：

- Sandbox 是否存在。
- 容器是否仍然运行。
- Agent 是否仍然持有租约。
- 当前是否有执行中的命令。
- Workspace 是否仍然可访问。

Heartbeat 超时不能直接等于任务失败。

需要先检查实际 Runtime 状态。

## 10.3 Sandbox Recovery

恢复流程：

```text
Agent Restart
     |
     v
Load Agent Session
     |
     v
Load Task State
     |
     v
Load Sandbox Metadata
     |
     v
Inspect Runtime
     |
     +-------------------+
     |                   |
     v                   v
Runtime Alive       Runtime Missing
     |                   |
     v                   v
Reconnect          Create New Sandbox
     |                   |
     +---------+---------+
               |
               v
        Verify Workspace
               |
               v
       Inspect Executions
               |
               v
       Reconcile Unknown
               |
               v
        Resume Agent Task
```

必须区分：

- Session Recovery
- Sandbox Recovery
- Workspace Recovery
- Execution Recovery
- Task Recovery

不能认为恢复对话记录就等于任务已经恢复。

# 11. 数据模型

至少需要以下核心实体。

## 11.1 Task

```typescript
interface Task {
  taskId: string;

  sessionId: string;

  status: string;

  workspaceId: string;

  sandboxId?: string;

  createdAt: string;

  updatedAt: string;
}
```

## 11.2 Sandbox

```typescript
interface Sandbox {
  sandboxId: string;
```

## 11.3 Execution

```typescript
interface Execution {
```

## 11.4 Workspace


# 13. 安全威胁模型

必须建立明确的 Threat Model。

## 13.1 需要防范的威胁

### 文件系统逃逸

攻击方式：

- `../`
- Symlink
- Hardlink
- Mount
- 特殊文件
- 竞态文件替换

预期结果：无法访问 Workspace 授权范围之外的宿主机文件。

### 进程逃逸

攻击方式：

- Fork Bomb
- Privilege Escalation
- Capabilities Abuse
- Namespace Manipulation
- Dangerous Syscalls

预期结果：无法获得宿主机高权限，资源使用受限。

### 网络攻击

攻击方式：

- SSRF
- DNS Rebinding
- IPv6 Bypass
- IP Literal
- Metadata Access
- Internal Port Scanning

预期结果：无法访问未经授权的内部服务。

### 容器管理接口攻击

攻击方式：

- Docker Socket Access
- containerd Socket Access
- OCI Config Injection
- Host Mount Injection

预期结果：Agent 无法创建高权限容器或修改宿主机运行环境。

### 凭证泄露

攻击方式：

- 环境变量读取
- 文件读取
- 日志泄露
- 子进程继承
- 网络外传

预期结果：不向 Sandbox 暴露不必要的长期凭证。

### 多 Task 越权

攻击方式：

- 猜测 Sandbox ID
- 猜测 Workspace ID
- 跨 Task 路径访问
- 共享可写存储
- 未授权执行请求

预期结果：所有对象都经过服务端 Task Ownership 校验。

## 13.2 安全边界

必须明确：

Permission Manager 负责授权决策。

Sandbox Runtime 负责执行层隔离。

Network Layer 负责网络隔离。

Credential Broker 负责凭证管理。

Audit Layer 负责追踪和审计。

不能把安全责任全部交给 Auto-review 或 LLM。

预期：

- Sandbox 销毁后 Workspace 仍存在。
- 新 Sandbox 可以重新挂载 Workspace。
- 文件内容和版本保持一致。

# 19. 故障处理原则

所有异常必须有明确的处理策略。

| 异常 | 处理方式 |
|---|---|
| Sandbox 创建失败 | 清理残留资源并返回错误 |
| Runtime 不可用 | 拒绝执行，不降级到 Host |
| Policy 服务不可用 | Fail Closed |
| Approval 服务不可用 | 需要审批的操作拒绝执行 |
| Workspace 不可用 | 暂停任务 |
| Network Proxy 不可用 | 网络操作失败关闭 |
| Sandbox OOM | 记录并终止任务执行 |
| Execution Timeout | 中断进程并记录结果 |
| Agent Crash | 恢复 Session 和 Task |
| Controller Crash | 重新扫描 Runtime 并恢复管理 |
| Unknown Execution | 核验外部状态，不盲目重试 |

核心原则：

**安全能力不可用时，不能自动退回到无隔离执行模式。**
