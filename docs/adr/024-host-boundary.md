# ADR 024：Host 头是安全边界

## 背景

服务默认只绑 `127.0.0.1`，并且没有登录。ADR 009 已经说明"身份是 handle，不是
认证"，所以"能连上这个端口"不能等于"可以读这个人的记忆"。ADR 022 为权限写接口
加了 loopback 检查、`Content-Type` 检查和每进程 token，注释里写的是"token 跨源页面
读不到，DNS rebinding 也猜不到"。

**后半句只对"猜"成立。** DNS rebinding 的做法是让攻击者的域名解析到 `127.0.0.1`：
浏览器仍然认为页面和请求同源，于是 `Origin` 和 `Host` 都是攻击者的域名，
`sameOrigin()` 比较两者自然相等；`GET /` 也会把 `<meta name="eunoia-token">`
交给这个页面。结果是本机 API 的全部读接口、`/api/chat`，以及默认开启的工作台
终端（它只需要一个同源页面就能加上的 `X-Workspace-UI` 头）都暴露给任意网页。

只绑 loopback 不是防线：它限制的是"谁能来"，而 rebinding 的请求就是从本机来的。

## 决定

1. **每个请求先校验 `Host`，在任何路由之前。** 默认接受
   `127.0.0.1` / `localhost` / `[::1]`，以及 `HOST` 显式指定的具体地址；其他名字
   必须在 `EUNOIA_ALLOWED_HOSTS` 里列出。不在名单上返回 403，不解析 URL、不读
   cookie、不生成身份。
2. **终端默认关闭。** 它不再跟着绑定地址走；`WORKSPACE_TERMINAL=1` 才开。
3. **终端额外要求 `X-Eunoia-Token`。** 同源判断和自定义头都不足以证明"这是本机
   的页面"，而终端是这套 HTTP 面里唯一会在宿主机上执行进程的路由。

## 后果

- `HOST=0.0.0.0` 或使用自定义域名时，必须同时设置 `EUNOIA_ALLOWED_HOSTS`，
  否则所有请求（包括 `/health`）都是 403。这是有意的：远程访问本来就需要先做
  认证，ADR 009 的阻塞项没有变。
- 反向代理如果改写 `Host`，要把对外域名加进名单；如果代理保留
  `Host: 127.0.0.1:8787`，则不需要。
- 工作台终端从"默认可用"变成"要显式打开"，这是一个行为变化，记录在
  `CHANGELOG.md` 的 Unreleased 里。
- `/health` 仍然会暴露工作区绝对路径。Host 校验把可读范围收回到本机名字，但
  没有引入认证；部署到公网之前，这条仍然要单独处理。

## 备选方案

- **在 `sameOrigin()` 里同时比较 `Sec-Fetch-Site` 和 `Origin`。** 不够：rebinding
  下浏览器报告的也是 `same-origin`，攻击者控制的两个值依然一致。
- **所有 `/api/*` 都要求 token。** 更彻底，但页面首次加载就要先拿 token，而
  `GET /` 本身还是得开放；把"哪些 Host 可以拿到页面"作为第一道锁更直接。
- **只靠认证。** 这是最终答案（ADR 009 的阻塞项），但不是现在能一次做完的事。
  Host 校验是认证之前就能生效、且不需要产品决策的一层。
