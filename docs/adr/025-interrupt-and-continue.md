# ADR 025 — 打断与继续（Interrupt and Continue）

**状态：** 已接受
**日期：** 2026-11-03
**相关：** ADR 006（客户端/服务端边界）、ADR 008（危机轮缓冲）、ADR 010（推理转发）、
ADR 014（agent loop）、ADR 016（SQLite）

---

## 1. 决策

一轮生成可以由用户中途停下，并且可以**从停下的位置继续**。三件事同时成立才算完成：

1. 聊天页在流式期间提供「停止」（按钮或 Esc），点下后本轮在服务端优雅结束；
2. 已经显示出来的半截回复**不丢弃**，作为 `messages.interrupted = 1` 落库；
3. 被打断的回合旁边出现「继续」，下一轮把半截回复作为历史、并带一条续写指令给模型。

这需要同时改事件契约、HTTP 层、回合编排、存储 schema 和前端；只加一个按钮不够。

## 2. 背景

改动之前，`AbortSignal` 已经贯穿了 `runTurn` → `streamReply` → `runAgentLoop` →
模型/工具，但只被一种情况触发：**客户端断开**（`res.on('close')`）。它解决的问题是
"人关了页面，别继续烧 token"，不是"人想停一下再说"。

因此：

- 前端没有任何停止入口，流式期间唯一能做的动作是等；
- 断开连接后，`runTurn` 只看到 runner 抛出的 `cancelled`，把这一轮记为 `failed` 并
  直接返回。**已经渲染在屏幕上的半截回复从数据库里消失**；
- 于是"继续"只能靠人重新说一遍，模型从头再答，既费 token 又会复述。

这不是一个可选体验。编码回合里一次工具调用可能跑几十秒，长回复可能写到一半才发现
方向不对；不能停的 agent 只能靠刷新页面，而刷新会连上下文一起丢掉。

## 3. 交互

| 状态 | 发送按钮 | 其他入口 |
|---|---|---|
| 空闲 | 箭头，`type=submit` | Enter 发送 |
| 流式中 | 方块，`type=button`，点击即停止 | `Esc` 停止（先关抽屉/菜单） |
| 停止中 | 禁用，`aria-label="正在停止…"` | 5 秒看门狗兜底断开 |
| 已停止 | 恢复箭头 | 回合下方「已打断 · 继续」 |

两个细节是有意的：

- **停止时不断开连接。** 正常路径是第二个请求 `POST /api/chat/stop`，原 SSE 连接继续
  读，直到服务端把半截回复落库并发出 `interrupted`。先 abort 再落库会丢掉要续写的
  内容，所以只有服务端已经找不到这一轮、或 5 秒内没有结束时，才把连接作为兜底切断。
- **「继续」不是"再说一句继续"。** 半截回复已经在历史里，续写指令只补充"从断点接着
  说、不要重开、不要复述"，不会替模型编造没说过的话。

## 4. 协议

### 4.1 请求

`POST /api/chat` 新增两个可选字段：

| 字段 | 类型 | 作用 |
|---|---|---|
| `turnId` | uuid | 客户端生成的回合 id，供停止请求寻址。缺省由服务端生成 |
| `continue` | boolean | 本轮是在续写上一轮；只在尾部上下文加续写指令 |

`turnId` 由客户端生成而不是等 `completed` 返回，是因为**第一轮**在 `completed` 之前
根本没有 `conversationId`，但人同样应该能停止它。

### 4.2 停止

`POST /api/chat/stop`，body `{ "turnId": "<uuid>" }`：

- 找到在途回合 → `abort()`，`200 {"stopped": true}`；
- 找不到（已结束/从未存在）→ `200 {"stopped": false}`。这是幂等状态查询，不是错误；
- 非 uuid → `400`。

服务端用 `Map<turnId, { controller }>` 登记在途回合，请求的 `finally` 里删除。停止
请求只负责投递 abort，**半截回复和 `interrupted` 事件仍然走原来的 SSE 流**——这样
客户端拿到的一定是已经落库的那一份。

### 4.3 事件

```ts
{ type: 'interrupted', text, conversationId?, messageId? }
```

- `text` 是停止时已经显示的部分；空字符串表示第一个可见字符之前就停了；
- 它是正常结束而不是 `error`：错误要报告，"被打断"要接着做；
- `conversationId` 让第一轮被打断的会话仍可继续；
- `messageId` 指向落库的那条 interrupted 消息（没有内容时为 null）。

旧客户端不认识这个事件类型，会像以前一样停在半截；服务端仍会落库，刷新后可见。

## 5. 持久化

schema v7：

1. `messages.interrupted INTEGER NOT NULL DEFAULT 0` —— 标记"这不是完整回复"。
2. `agent_runs.status` 的 CHECK 增加 `'interrupted'` —— 停止既不是 `failed` 也不是
   `completed`，把它算成失败会污染运行统计。

第 2 条不能 `ALTER TABLE`：SQLite 不能修改 CHECK 约束，只能重建表。迁移
（`migrateToVersion7`）的做法是"建新表 → 拷贝 → 删旧表 → 改名 → 重建索引"，并且
处理了"崩在 DROP 和 RENAME 之间"的情况：此时 `agent_runs_v7` 是唯一副本，下次打开
应当完成改名，而不是从一张已不存在的表重建。

`Message.interrupted` 在 `toMessage` 边界转换成 boolean；内存实现同样返回该字段，
两个存储的契约保持一致。

## 6. 续写提示

续写指令放在**本轮尾部上下文**（`buildRuntimeContext` 的 `continuationBlock`），不写进
系统提示词，也不改写用户消息：

- 系统提示词是稳定前缀，改它会让人格/历史缓存全部失效；
- 用户消息应当保留人真正说的话（界面上就是「继续」）；
- "怎么续写"是这一轮的指令，不是关于这个人的事实。

指令内容要求从断点继续、保持语气和话题、不重开、不复述、不解释自己被打断。

## 7. 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只加停止按钮，不落库 | 停止后历史缺一块，"继续"只能重答；刷新后连半截都没了 |
| 停止 = 直接 abort 连接 | 服务端来不及落库；客户端也拿不到 `messageId` / `conversationId` |
| 客户端把半截文本随"继续"请求发回服务端 | 服务端有了两份真相：历史里的和请求里的；截断/篡改也无法校验 |
| SSE 断线续传（`Last-Event-ID` 重放） | 解决的是网络重连，不是用户主动停止；事件缓冲是另一套复杂度 |
| 把 `interrupted` 记成 `failed` | 用户主动停止不是失败；会拉低成功率、误导评测 |
| 把半截回复写成普通 assistant 消息 | UI 无法区分"说完了"和"说到一半"，模型也会以为自己说完了 |

## 8. 测试

- **service**：半截回复落库且 `interrupted=true`；空半截只留用户消息；`continue` 的
  history/上下文包含断点与续写指令；普通回合没有续写指令。
- **api**：`turnId`/`continue` 校验；停止未知回合返回 `stopped:false`；真实慢流被停止
  后，SSE 末帧是 `interrupted`，且 `GET /messages` 能看到 `interrupted=true`；续写能
  读到半截回复。
- **db**：`interrupted` 布尔往返；v6 文件迁移后列存在、旧行保留、CHECK 接受
  `'interrupted'`。
- **web**：`interrupted` 帧保留半截文本并给出「继续」；继续请求带同一
  `conversationId` 与 `continue:true`；历史回放只给最后一条 interrupted 消息继续按钮；
  流式中按钮变停止并发出带同一 `turnId` 的停止请求。

## 9. 后果与边界

- **不覆盖进程崩溃恢复。** 服务端重启后，在途回合不会自动续跑；已经落库的半截回复
  仍可手动「继续」。事件溯源式的自动恢复是另一个量级的工作，见
  `docs/myfree/Agent/dsh恢复机制.md`。
- **工具副作用不回收。** 停止会 abort 工具的 signal（命令会被杀），但已经写下的文件
  不会回滚；沙箱的 interrupt 语义仍由 ADR 017/018 管。
- **危机回合仍不流式。** 停止只会得到空的 `interrupted`，安全替换逻辑不受影响。
- **断线也会落库。** 客户端断开连接同样走 `cancelled` 路径，因此刷新页面后还能看到
  被打断的半截回复；这是有意的，和"主动停止"在数据层同构。
- **旧客户端兼容。** 不发送 `turnId` 仍可正常聊天，只是不能停止；不认识 `interrupted`
  事件的客户端会忽略它，半截内容仍在库里。
