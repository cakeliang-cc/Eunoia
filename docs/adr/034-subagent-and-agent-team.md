# ADR 034 — Subagent 运行时与 Agent Team 协作

状态：已实施（核心范围）；限制见文末与[验收报告](../features/eunoia-AgentTeam验收报告.md)。
日期：2026-11-08。部分替代 [ADR 001](./001-single-agent.md)：本文只扩展"可委派的执行成员"与"持久任务板"，不改变普通聊天仍由单 Agent 承载的事实。

## 背景

产品需要把可分离的工作交给独立成员：成员有自己的上下文、模型请求、工具循环和取消信号；主 Agent 负责任务拆分、验收和集成。DSH 的 Agent Team 用 Subagent 运行时加持久任务板实现，Codex 用独立子线程实现委派；这两者都不是"一个提示词写多个角色"，也不是"并行只读工具"。

原来的单 Agent 架构没有成员、任务归属、依赖、并发认领、全队预算或故障恢复。直接把这些塞进 `src/agent/loop.ts` 会让模型循环依赖任务板策略；把成员做成第二套执行路径则会绕过权限、轨迹和幂等。

## 决定

1. **一条执行路径。** 成员执行复用 `runAgentLoop`，和主对话相同的 `DurableTranscript`、工具注册、策略、执行记录与取消语义。成员不是第二个 agent 实现。
2. **三层对象。** `Member`（持久参与者）、`Activation`（成员的一次执行）、`Task`（需要验收的工作）分开建模。`activation.succeeded` 只表示这次执行正常结束，绝不等于任务通过或 Team 成功。
3. **独立内部会话。** 每个成员有自己的内部 conversation，普通会话列表过滤掉它们；`fresh` 从零开始，`fork` 只复制已提交、未中断的轮次，且父权限必须覆盖子权限，否则拒绝 fork。
4. **持久任务板与 CAS。** `TeamStore` 是端口，内存与 SQLite 共用契约。任务修改携带 `expectedRevision`；认领是带状态与版本条件的单条更新；事件与状态在同一事务写出。
5. **邮箱在步骤边界注入。** 忙成员的消息在下一次模型请求前作为带来源的协作数据注入，并写入模型轨迹；不会插进工具调用组中间。`clientMessageId + sender + recipient` 幂等。
6. **预算与并发许可是两个计数。** 每个 provider 请求前原子预留输入估算与最大输出；模型 HTTP 并发用按 run 的信号量。等待成员不占模型许可（`agent_wait` 不使用信号量）。
7. **隔离工作区。** 可写成员使用源目录的私有副本；快照排除密钥、忽略目录和越界链接；产物记录基线与内容哈希；集成冲突显式保留，不覆盖用户源目录。
8. **恢复不重放。** 启动时把过期的 running activation 标记为 interrupted/unknown；迟到回调检查 generation；停止后不能被迟到结果改成成功。

## 边界

- 普通聊天仍然是单 Agent；Team 只在显式创建 run 时启用。
- 任务板关闭（`mode=delegation`）仍允许 Subagent 委派，保留历史记录。
- `writeScopes` 只是调度提示，不是锁；文件权限由沙箱工具策略执行。
- 模型能力来自 catalog，不从模型名字猜；未知模型/不支持工具直接拒绝。

## 取舍

- **每人一个内部 conversation 而不是内存上下文。** 多写一行 conversation，换来可恢复、可审计、可 fork 的历史；代价是会话列表必须显式过滤。
- **任务事件与状态同事务。** 存储层方法因此接收可选的 event 参数，接口比"先改状态再发事件"啰嗦，但崩溃时不会出现"状态变了没人知道"。
- **全队 24 次请求的默认预算** 是防失控的工程选择，不是性能结论。真实 E06 运行在 24 次请求时仍未完成第三个必需任务，被正确记为 `waiting_user` 而不是成功（见验收报告）。
