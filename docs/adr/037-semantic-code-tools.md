# ADR 037：语义代码工具（定义、引用、诊断）

日期：2026 年 11 月 8 日。状态：已实现（TypeScript/JavaScript）。

## 1 背景

编码工具原本只有搜索、读取、编辑和命令执行。`grep` 能回答“这个字符串出现在哪里”，
但用户说“修改这个函数并检查所有调用点”时，文本搜索会把同名但无关的局部函数也算进来，
也会漏掉别名/重导出。符号定义、引用和类型诊断需要语言服务，而不是正则。

## 2 决定一：先做真实可用的 TypeScript 语义，不用文本搜索冒充

工具直接使用仓库已有的 `typescript` 编译器 API（`createLanguageService`）：

- `find_definition`：位置或符号名 → 定义位置（可跨文件）；
- `find_references`：语义引用，区分同名不同符号，可选是否包含声明；
- `diagnostics`：语法 + 语义诊断，带 `path:line:col TSxxxx`。

位置支持 1-based 行列，或一个 `symbol` 名字。后者用 TypeScript scanner 找**标识符 token**，
不是子串；`add` 不会匹配 `address`。

## 3 决定二：有界、只读、可消失

每次调用构建一个工作区快照：

- 通过 `ToolWorkspacePort.glob/readLines` 读取，和 `read_file` 走同一套路径守卫、忽略
  规则和大小限制；
- 最多 800 个文件 / 8 MiB，超出在结果里明说“只加载了前 N 个”；
- 不常驻 daemon，不写索引文件，不执行命令；
- 标准库没有加载，因此过滤少量“找不到全局名”的诊断码，避免噪声淹没真实错误。

`readLines` 面向模型会加行号前缀，语言服务必须看到真实字节，因此加载时去掉该前缀。

## 4 决定三：不支持的语言明确拒绝

`.py`、`.go`、`.rs` 等文件返回 `SEMANTIC_UNSUPPORTED` 的可读错误，而不是退化成文本
搜索。退化会回答一个不同的问题，而且看起来像成功——这正是本 ADR 要避免的失败模式。

LSP 是后续可插的适配器方向：`SemanticProject` 这层接口（文件集合 + 定义/引用/诊断）
可以换成真正的 LSP 客户端，而不改工具契约。当前没有引入语言服务器进程：沙箱里的
文件、进程生命周期和权限边界都还没有为它设计，先做本机可用、可测试的语义能力。

## 5 决定四：与现有工具的关系

语义工具只是新增的只读工具，不替代 `grep`（文本/日志/非代码文件仍需要它），也不
自动改代码。模型先用 `find_definition`/`find_references` 确认影响面，再用 `edit_file`
或 `bash` 修改，最后用 `diagnostics` 检查。

## 6 后果

**收益**：跨文件调用点可以准确找到；改签名前能看清影响面；编辑后能直接得到类型错误。

**边界**：

- 只支持 TS/JS；不支持的语言必须显式失败；
- 不加载项目 `node_modules` 的类型包，第三方库的复杂类型可能缺失；无法解析的包
  导入会被过滤，真实相对导入错误仍会报告；
- 快照上限之外的文件不在结果里，工具会说明，而不是声称“没有引用”；
- 不替代项目自己的 tsconfig/路径别名；它使用一组保守的编译选项，不是完整构建配置。
