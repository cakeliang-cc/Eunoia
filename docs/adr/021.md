# Eunoia — Task-scoped CWD 完整重构实施方案

**项目：** designFree / Eunoia  
**模块：** Agent Runtime / Coding Tools / Sandbox Runtime  
**重构主题：** Stateless Bash + Stateful Task CWD  
**设计选择：** A — Agent 级目录状态  
**实施方式：** 在现有 Sandbox 架构上完成一次性完整重构

---

# 0. 核心架构决策

## 0.1 最终设计

Eunoia 采用：

**Stateless Bash Execution + Stateful Task Context + Runtime-managed CWD**

具体含义：

1. 每次 `run_command` 都创建独立的 Shell Execution。
2. Bash 不保留上一次调用的当前工作目录。
3. Agent Runtime 为每个 Task 维护唯一的逻辑工作目录。
4. 每次 Bash Execution 启动前，Runtime 读取当前 Task CWD。
5. Runtime 将 CWD 注入 Sandbox Gateway。
6. Gateway 验证 CWD 是否属于当前 Task 的 Workspace。
7. OCI Runtime 在指定 CWD 启动命令。
8. Agent 通过 `change_directory` 显式更新后续 Execution 的 CWD。
9. CWD 与 Task 生命周期绑定，持久化并支持恢复。

## 0.2 明确不采用的方案

本次不采用：

- Persistent Bash 作为默认执行模型。
- 从 Bash 命令文本中解析 `cd`。
- 通过 LLM 对话历史推断 CWD。
- 每次 Execution 固定使用 `/workspace`。
- 由 Agent 自己提交可信的绝对工作目录。
- 由 Bash Execution 结果自动覆盖 Task CWD。
- 将 CWD 直接绑定到 Sandbox Container 的全局状态。

## 0.3 最终状态归属

| 状态 | 所属模块 | 生命周期 |
|---|---|---|
| Workspace Root | Workspace Manager | Workspace |
| Task CWD | Agent Runtime / Task Context | Task |
| Execution CWD | Execution Context | 单次 Execution |
| Bash Variables | Shell Process | 单次 Execution |
| Shell Environment | Execution Environment | 单次 Execution |
| Files | Workspace | Workspace |
| Background Processes | Process Manager | 独立进程生命周期 |
| Sandbox Container | Sandbox Runtime | Sandbox |
| Task Progress | Agent Runtime | Task |

关键规则：

**Task CWD 是唯一可信的默认工作目录状态。Execution CWD 是创建 Execution 时读取的不可变快照。**

# 2. 数据模型

## 2.1 TaskExecutionContext

建议在现有 Task 模型中扩展，不要另建一份与 Task 生命周期脱节的上下文。

```typescript
export interface TaskExecutionContext {
  taskId: string;
  sandboxId: string;

  workspaceId: string;
  workspaceRoot: string;

  cwd: string;
  cwdVersion: number;

  status: "active" | "completed" | "cancelled";

  createdAt: string;
  updatedAt: string;
}
```

示例：

```json
{
  "taskId": "task_123",
  "sandboxId": "sandbox_456",
  "workspaceId": "workspace_789",
  "workspaceRoot": "/workspace",
  "cwd": "/workspace/project/src",
  "cwdVersion": 4,
  "status": "active"
}
```

## 2.2 字段约束

### workspaceRoot

- 由 Workspace Manager 提供。
- 不允许 Agent 修改。
- 不允许 `change_directory` 修改。
- 必须是 Sandbox 内 Workspace 的规范根目录。
- 不允许从请求参数中直接信任。

### cwd

- 必须是绝对路径。
- 必须位于当前 Task 的 Workspace 授权范围内。
- 必须对应存在的目录。
- 不允许指向文件。
- 不允许指向已经失效的 Workspace。
- 不允许跨 Sandbox 使用。

### cwdVersion

每次成功修改 CWD 时递增。

```text
Initial:
  cwd = /workspace
  version = 1

Change:
  cwd = /workspace/src
  version = 2

Change:
  cwd = /workspace/tests
  version = 3
```

版本号用于并发控制、Execution 快照和恢复验证。

## 2.3 数据库迁移

如果 Task 已有数据库记录，优先扩展 Task 表。

示例：

```sql
ALTER TABLE tasks
ADD COLUMN workspace_root TEXT,
ADD COLUMN current_cwd TEXT,
ADD COLUMN cwd_version INTEGER NOT NULL DEFAULT 1;
```

实际字段名与类型以项目当前数据库和 ORM 为准。

约束：

- `workspace_root` 创建 Task 时初始化。
- `current_cwd` 默认等于 `workspace_root`。
- `cwd_version` 初始为 1。
- 不允许通过普通 Task Update 接口随意修改这三个字段。
- CWD 更新必须经过专用事务接口。

如果项目已有 Event Store，则 CWD 变更也应写入 Event Log；当前值可以作为 Task Projection 持久化。

# 3. TaskContextStore 接口

所有模块必须通过统一接口访问 CWD。

```typescript
export interface TaskContextStore {
  get(taskId: string): Promise<TaskExecutionContext>;

  initialize(
    input: InitializeTaskContextInput
  ): Promise<TaskExecutionContext>;

  updateCwd(
    input: UpdateTaskCwdInput
  ): Promise<TaskExecutionContext>;

  snapshot(
    taskId: string
  ): Promise<TaskExecutionContext>;

  close(taskId: string): Promise<void>;
}
```

输入类型：

```typescript
export interface InitializeTaskContextInput {
  taskId: string;
  sandboxId: string;
  workspaceId: string;
  workspaceRoot: string;
}

export interface UpdateTaskCwdInput {
  taskId: string;
  expectedVersion: number;
  newCwd: string;
}
```

## 3.1 原子更新

`updateCwd` 必须使用数据库事务或等价的原子 CAS 操作。

SQL 示例：

```sql
UPDATE tasks
SET
  current_cwd = :newCwd,
  cwd_version = cwd_version + 1,
  updated_at = CURRENT_TIMESTAMP
WHERE
  id = :taskId
  AND cwd_version = :expectedVersion
  AND status = 'active';
```

如果更新行数为 0：

- Task 不存在；
- Task 已结束；
- 或 CWD Version 已过期。

必须返回明确的错误，不能静默覆盖。

```typescript
export class CwdVersionConflictError extends Error {}
```

## 3.2 事务与事件

一次成功的 CWD 更新必须保证：

1. Task CWD 更新成功。
2. Version 递增。
3. CWD Changed Audit Event 写入成功，或进入可靠的事务 Outbox。
4. 不允许只更新内存而不持久化。
5. 不允许只写 Audit 而 CWD 更新失败却报告成功。

推荐使用 Transactional Outbox，避免数据库状态与异步事件不一致。

# 4. CwdManager

`CwdManager` 是目录变更的业务入口。

```typescript
export interface CwdManager {
  getCurrentDirectory(
    taskId: string
  ): Promise<CwdResult>;

  changeDirectory(
    input: ChangeDirectoryInput
  ): Promise<ChangeDirectoryResult>;
}
```

类型：

```typescript
export interface ChangeDirectoryInput {
  taskId: string;
  path: string;
  expectedCwdVersion?: number;
}

export interface CwdResult {
  cwd: string;
  workspaceRoot: string;
  cwdVersion: number;
}

export interface ChangeDirectoryResult {
  success: true;
  previousCwd: string;
  cwd: string;
  cwdVersion: number;
}
```

## 4.1 相对路径解析

相对路径以 Task 当前 CWD 为基准。

假设：

```text
workspaceRoot = /workspace
cwd = /workspace/project
```

执行：

```text
changeDirectory("src")
```

结果：

```text
/workspace/project/src
```

执行：

```text
changeDirectory("../tests")
```

结果：

```text
/workspace/tests
```

执行：

```text
changeDirectory("/")
```

结果：

```text
/
```

但由于 `/` 不在 Workspace 内，必须拒绝。

## 4.2 路径处理流程

```text
Change Directory Request
          |
          v
Load Task Context
          |
          v
Check Task Status
          |
          v
Check Expected CWD Version
          |
          v
Resolve Relative Path
          |
          v
Check Workspace Boundary
          |
          v
Check Permission Policy
          |
          v
Validate Directory in Sandbox
          |
          v
Atomic CWD Update
          |
          v
Audit Event
          |
          v
Return New CWD
```

## 4.3 路径安全

不能仅通过字符串前缀判断 Workspace 边界。

错误实现：

```typescript
if (target.startsWith(workspaceRoot)) {
  return true;
}
```

因为：

```text
/workspace-evil
```

也可能通过：

```text
/workspace
```

的字符串前缀检查。

最低要求：

1. 使用 `path.resolve` 规范化词法路径。
2. 使用 `path.relative` 判断路径包含关系。
3. 验证目标是目录。
4. 验证实际解析路径仍然位于 Workspace 内。
5. 检查符号链接。
6. 检查 Workspace 是否仍然挂载到当前 Sandbox。
7. 拒绝无法验证的路径。

示例：

```typescript
import path from "node:path";

function isWithinRoot(
  root: string,
  target: string
): boolean {
  const relative = path.relative(root, target);

  return (
    relative === "" ||
    (
      relative !== ".." &&
      !relative.startsWith(`..${path.sep}`) &&
      !path.isAbsolute(relative)
    )
  );
}
```

注意：

这段函数只能作为词法路径检查，不能单独作为安全边界。

实际路径检查必须在 Sandbox 内完成，避免符号链接和路径竞争造成逃逸。

## 4.4 Symlink 和 TOCTOU

例如：

```text
/workspace/project/link -> /etc
```

Agent 请求：

```text
changeDirectory("link")
```

即使词法路径在 Workspace 内，真实路径也已经逃逸。

因此，Sandbox Runtime 必须进行实际路径验证。

推荐在 Linux Runtime 中使用基于 Workspace 根目录文件描述符的安全路径解析机制，例如 `openat2`：

- `RESOLVE_BENEATH`
- `RESOLVE_NO_MAGICLINKS`
- 必要时使用 `RESOLVE_NO_SYMLINKS`

或者采用经过审计的等价实现。

验证目标目录后，尽量使用已验证的文件描述符执行 `fchdir`，避免验证与实际进入目录之间的 TOCTOU 竞争。

不要仅依赖：

```bash
realpath "$target"
```

然后再单独启动另一个进程使用路径。两次操作之间可能发生符号链接变化。

如果当前 OCI 执行链路不能直接传递已验证的目录文件描述符，应在容器内增加受控的执行启动器，由启动器在同一进程内完成路径解析、目录切换和命令启动。

# 5. 新增 change_directory Tool

## 5.1 工具定义

建议新增：

```text
src/tools/coding/change-directory-tool.ts
```

工具名称：

```text
change_directory
```

输入 Schema：

```typescript
export interface ChangeDirectoryToolInput {
  path: string;
}
```

不建议让 Agent 提交：

- taskId
- sandboxId
- workspaceRoot
- cwdVersion

这些都应由可信 Runtime 上下文提供。

工具实现：

```typescript
export function createChangeDirectoryTool(
  cwdManager: CwdManager,
  context: ToolContext
) {
  return {
    name: "change_directory",

    description:
      "Change the current working directory for the current task. " +
      "Relative paths are resolved against the current task directory. " +
      "The target must be inside the task workspace. " +
      "Subsequent shell executions will start in the new directory.",

    inputSchema: {
      type: "object",
      properties: {
        path: {
          type: "string",
          description:
            "Absolute or relative directory path within the task workspace."
        }
      },
      required: ["path"],
      additionalProperties: false
    },

    execute: async (
      input: ChangeDirectoryToolInput
    ) => {
      return cwdManager.changeDirectory({
        taskId: context.taskId,
        path: input.path
      });
    }
  };
}
```

具体 Tool 类型应复用项目现有 `codingTools` 注册规范。

## 5.2 工具返回结果

成功：

```json
{
  "success": true,
  "previousCwd": "/workspace/project",
  "cwd": "/workspace/project/src",
  "cwdVersion": 2
}
```

失败：

```json
{
  "success": false,
  "error": "DIRECTORY_NOT_FOUND",
  "message": "The requested directory does not exist."
}
```

错误类型至少包括：

- `DIRECTORY_NOT_FOUND`
- `NOT_A_DIRECTORY`
- `PATH_OUTSIDE_WORKSPACE`
- `SYMLINK_ESCAPE`
- `TASK_NOT_ACTIVE`
- `CWD_VERSION_CONFLICT`
- `PERMISSION_DENIED`
- `SANDBOX_UNAVAILABLE`

不要把内部宿主机路径、敏感文件信息或 Runtime 堆栈直接暴露给 Agent。

# 6. run_command 改造

这是本次最重要的执行链路修改。

## 6.1 保持 Agent 工具输入简单

原有输入：

```typescript
interface RunCommandInput {
  command: string;
  timeout_ms?: number;
}
```

建议继续保留。

不要强迫 LLM 每次传入 `workdir`。

原因：

- Agent 可能填写错误路径。
- Agent 可能使用历史上下文中的过期路径。
- Agent 不应成为 CWD 的可信来源。
- Runtime 已经掌握 Task CWD。

如果以后需要显式覆盖目录，应采用独立的受控接口，而不是默认信任模型参数。

## 6.2 Tool Adapter 改造

原有逻辑：

```typescript
cwd: WORKSPACE_MOUNT_PATH
```

改为：

```typescript
const taskContext =
  await taskContextStore.snapshot(context.taskId);

const result = await sandboxGateway.execute({
  taskId: context.taskId,
  sandboxId: taskContext.sandboxId,

  command: [input.command],
  shell: true,

  cwd: taskContext.cwd,
  cwdVersion: taskContext.cwdVersion,

  toolCallId: context.toolCallId,
  timeoutMs: input.timeout_ms
});
```

以上为目标接口示例，应与现有 Gateway Request 类型合并。

## 6.3 Execution CWD Snapshot

每次 Execution 创建时必须记录：

```typescript
export interface ExecutionContextSnapshot {
  taskId: string;
  sandboxId: string;

  workspaceId: string;
  workspaceRoot: string;

  cwd: string;
  cwdVersion: number;

  policyVersion: number;
}
```

该快照在 Execution 生命周期内不可修改。

例如：

```json
{
  "executionId": "exec_001",
  "taskId": "task_123",
  "cwd": "/workspace/project/src",
  "cwdVersion": 4
}
```

即使 Task CWD 后续更新为：

```text
/workspace/project/tests
```

已经启动的 Execution 仍然使用自己的快照。

这可以保证 Execution 结果可解释、可审计。

## 6.4 Gateway 二次校验

Gateway 不应直接信任 Tool Adapter 传来的 `cwd`。

建议：

1. 根据 Task ID 读取可信 Task Context。
2. 确认 Sandbox ID 匹配。
3. 确认 Workspace ID 匹配。
4. 验证 CWD 与当前 Task CWD 快照一致。
5. 验证 CWD 仍然在 Workspace 范围内。
6. 验证权限策略。
7. 创建 Execution Snapshot。
8. 交给 Runtime 执行。

如果 CWD Version 不匹配：

```text
CWD_VERSION_MISMATCH
```

应重新读取 Task Context，而不是猜测目录。

# 7. OCI Runtime 改造

## 7.1 现有实现

当前类似：

```text
docker exec
  --user 1000:1000
  --workdir /workspace
  <container>
  /bin/sh -c <wrapper>
```

改造后：

```text
docker exec
  --user 1000:1000
  --workdir <validated-cwd>
  <container>
  /bin/sh -c <wrapper>
```

例如：

```text
--workdir /workspace/project/src
```

## 7.2 参数构建

```typescript
export interface OciExecutionOptions {
  containerId: string;
  user: string;
  cwd: string;
  command: string;
}
```

参数构建：

```typescript
function buildExecArgs(
  options: OciExecutionOptions
): string[] {
  return [
    "exec",
    "--user",
    options.user,
    "--workdir",
    options.cwd,
    options.containerId,
    "/bin/sh",
    "-c",
    options.command
  ];
}
```

必须继续使用数组形式传递参数，不允许将用户命令拼接到宿主机 Shell 字符串中执行。

## 7.3 关于 `/bin/sh` 和 `/bin/bash`

当前实现描述为：

```text
/bin/sh -c "<command>"
```

这与完整 Bash 语义不同。

本次 CWD 重构不应顺便无条件改变 Shell 兼容性。

应先核实：

- 当前镜像中的 `/bin/sh` 实际指向什么。
- Coding Tool 对 Bash 语法的承诺是什么。
- Wrapper 如何传递退出码。
- Execution Marker 是否依赖特定 Shell 行为。

如果项目承诺 Bash，应明确配置 Bash Binary 并测试其语义。

如果项目只承诺 POSIX Shell，应保留 `/bin/sh`，并明确工具文档。

无论使用哪种 Shell，CWD 机制都不应依赖 Shell 进程持久化。

# 8. Agent Runtime 集成

## 8.1 Task 初始化

Task 创建成功后：

```typescript
const taskContext =
  await taskContextStore.initialize({
    taskId,
    sandboxId,
    workspaceId,
    workspaceRoot: WORKSPACE_MOUNT_PATH
  });
```

初始状态：

```text
cwd = workspaceRoot
cwdVersion = 1
```

Task Context 必须在 Coding Tools 注册和首次执行前准备好。

## 8.2 Tool 注册

原来：

```typescript
const codingTools = [
  createCommandTool(...)
];
```

改为：

```typescript
const codingTools = [
  createCommandTool(...),
  createChangeDirectoryTool(...)
];
```

具体注册方式沿用现有 Tool Registry。

## 8.3 Agent Loop

不需要让 Agent Loop 直接实现路径解析。

Agent Loop 只负责：

- 提供当前 Task Context。
- 注册 `change_directory`。
- 调度 Tool Execution。
- 将工具结果返回模型。

CWD 业务逻辑必须留在 CwdManager。

## 8.4 工具描述

`run_command` 描述应明确：

- 命令在当前 Task 的工作目录中执行。
- 每次调用使用独立 Shell。
- 当前目录由 Runtime 管理。
- `cd` 只影响当前命令进程，不改变后续调用的 Task CWD。
- 要改变后续命令的工作目录，必须调用 `change_directory`。

`change_directory` 描述应明确：

- 相对路径基于当前 Task CWD。
- 绝对路径必须位于 Workspace 内。
- 成功后后续 `run_command` 自动使用新目录。
- 不会改变宿主机工作目录。

# 9. 权限系统集成

复用现有：

```text
src/sandbox/permissions/
```

不需要另建 CWD 专用审批系统。

## 9.1 目录变更的权限判定

`change_directory` 应经过 Permission Manager。

建议增加动作类型：

```typescript
type PermissionAction =
  | "workspace.read"
  | "workspace.write"
  | "workspace.change_directory"
  | "command.execute";
```

普通 Workspace 内目录切换可以默认允许。

以下情况应拒绝或按策略处理：

- 目标目录不在 Workspace 内。
- 目标目录违反项目级访问策略。
- 目标目录指向敏感挂载。
- Task 已结束。
- Workspace 已失效。

CWD 变更本身不等于授予目录读写权限。

**改变当前目录不能扩大文件系统权限。**

## 9.2 权限模式兼容

| Permission Mode | change_directory |
|---|---|
| `read-only` | 允许在只读授权范围内切换 |
| `auto` | Workspace 范围内自动允许 |
| `on-request` | 超出已有策略的权限请求进入审批，但不能突破 System Deny |
| `restricted` | 仅允许白名单目录 |

目录切换和文件操作必须分别判权。

# 10. 并发控制

## 10.1 基本原则

同一个 Task 可以有多个 Execution，但 Task CWD 只能有一个当前值。

每个 Execution 使用创建时的 CWD Snapshot。

## 10.2 目录变更串行化

建议同一个 Task 的 `change_directory` 使用串行队列或数据库 CAS。

示例：

```text
Initial:
  cwd = /workspace
  version = 1

A: change_directory("src")
B: change_directory("tests")

A:
  expectedVersion = 1
  success
  cwd = /workspace/src
  version = 2

B:
  expectedVersion = 1
  conflict
```

B 必须重新读取当前 CWD，再根据新的基准路径决定是否重试。

不能在内部静默把原始相对路径换一个基准重新执行。

## 10.3 并发 Bash

假设：

```text
Execution A:
  cwd = /workspace/src
  command = npm test

Execution B:
  cwd = /workspace
  command = git status
```

两条命令可以并发执行。

它们不共享 Shell CWD。

如果两个 Execution 都读取了相同版本的 Task CWD，后续发生目录变更也不应该偷偷修改已创建的 Execution Snapshot。

## 10.4 顺序依赖

Agent 明确需要：

```text
change_directory("src")
run_command("npm test")
```

必须保证第二个 Tool Call 在第一个成功后执行。

如果 Agent Loop 支持并发 Tool Calls，应增加工具依赖或同 Task 状态变更的调度规则。

不能只依赖 LLM 自己理解执行顺序。

# 11. Recovery 与持久化

## 11.1 需要持久化的状态

至少持久化：

- Task CWD。
- CWD Version。
- Workspace Root。
- Sandbox ID。
- Execution CWD Snapshot。
- Execution Status。
- Policy Version。
- CWD Change Audit Event。

## 11.2 Agent 重启

恢复流程：

```text
Agent Restart
      |
      v
Restore Session
      |
      v
Restore Task
      |
      v
Restore Workspace Binding
      |
      v
Restore Task CWD
      |
      v
Validate Sandbox Binding
      |
      v
Validate Workspace Mount
      |
      v
Validate CWD Existence
      |
      v
Resume Agent Loop
```

## 11.3 CWD 不存在

例如 Task 恢复后，原目录：

```text
/workspace/project/src
```

已经被删除。

此时：

- 不允许静默使用旧路径。
- 不允许自动切换到 `/workspace` 后继续执行。
- 不允许让 LLM 猜测原目录是否仍然存在。

建议恢复结果：

```json
{
  "status": "cwd_invalid",
  "previousCwd": "/workspace/project/src",
  "reason": "DIRECTORY_NOT_FOUND"
}
```

进入受控恢复流程：

1. 保留原始 CWD 记录。
2. 暂停该 Task 的命令执行。
3. 由 Runtime 检查 Workspace。
4. 如果能够确定性恢复原目录，则恢复。
5. 否则进入明确的恢复决策。
6. 恢复成功后递增 CWD Version 并写入 Audit。

## 11.4 Sandbox 丢失

如果 Sandbox 被重建：

- 先恢复 Workspace。
- 再验证原 CWD。
- 再恢复 Task Context。
- 不恢复已死亡的 Bash 进程。
- 不恢复不存在的后台进程。
- 对 UNKNOWN Execution 继续使用现有 Execution Recovery 机制。

CWD 恢复与 Execution Recovery 是两件独立的事。

## 11.5 持久化边界

不要把 CWD 只存在于内存 Map。

内存可以缓存：

```typescript
Map<TaskId, TaskExecutionContext>
```

但数据库或现有可靠 Persistence 才是权威状态源。

进程重启后必须能够重建。

# 12. Execution 与 CWD 的一致性

## 12.1 Execution 创建时冻结快照

创建 Execution 时：

```typescript
const context =
  await taskContextStore.snapshot(taskId);

const execution = await executionStore.create({
  taskId,
  sandboxId: context.sandboxId,
  cwd: context.cwd,
  cwdVersion: context.cwdVersion
});
```

## 12.2 Execution Event

建议增加：

```text
execution.cwd.snapshot
task.cwd.changed
task.cwd.recovered
task.cwd.invalidated
```

每次执行都能追溯：

- 当时的 CWD。
- 当时的 CWD Version。
- 对应 Workspace。
- 对应 Sandbox。
- 对应 Policy Version。

## 12.3 幂等性

`change_directory` 应支持幂等请求标识。

如果请求因为网络超时导致客户端重试：

- 不应重复递增 Version。
- 不应重复产生两个不同结果。
- 应返回原始请求的结果。

建议使用现有 Tool Call ID 或新增 `operationId`。

如果同一个 operationId 携带不同参数，必须拒绝。

# 13. 错误处理

定义稳定错误类型：

```typescript
export type CwdErrorCode =
  | "TASK_NOT_FOUND"
  | "TASK_NOT_ACTIVE"
  | "SANDBOX_NOT_FOUND"
  | "WORKSPACE_NOT_AVAILABLE"
  | "DIRECTORY_NOT_FOUND"
  | "NOT_A_DIRECTORY"
  | "PATH_OUTSIDE_WORKSPACE"
  | "SYMLINK_ESCAPE"
  | "PERMISSION_DENIED"
  | "CWD_VERSION_CONFLICT"
  | "CWD_VERSION_MISMATCH"
  | "CWD_INVALID"
  | "EXECUTION_CONTEXT_INVALID"
  | "IDEMPOTENCY_CONFLICT";
```

处理原则：

- 明确的业务错误返回结构化结果。
- Runtime 不可用时不更新 CWD。
- 数据库更新失败时不报告成功。
- Sandbox 校验失败时不启动命令。
- 无法确认状态时 Fail Closed。
- 不允许自动回退到 `/workspace` 继续执行。

# 16. 兼容迁移

## 16.1 初始迁移

现有 Task 没有 CWD 字段时：

```text
workspaceRoot = /workspace
cwd = /workspace
cwdVersion = 1
```

不要尝试从历史 Bash 命令中恢复目录。

原因：

历史命令中的 `cd` 可能发生在：

- 子 Shell。
- 脚本。
- 函数。
- 条件语句。
- 已经结束的 Execution。

无法可靠地推断父 Shell 的最终 CWD。

## 16.2 工具兼容

旧工具：

```text
run_command(command, timeout_ms)
```

继续保留输入结构。

内部执行改为：

```text
run_command(command, timeout_ms, runtimeInjectedCwd)
```

新工具：

```text
change_directory(path)
```

由 Tool Registry 注册。

## 16.3 迁移原则

- 不改变原有 Sandbox Container 的隔离策略。
- 不改变 Execution ID 的语义。
- 不改变原有 UNKNOWN Recovery 语义。
- 不改变现有工具结果结构，除非必须增加字段。
- 不允许保留固定 `/workspace` 的静默回退路径。
- 不允许出现新旧两套 CWD 状态同时生效。

# 20. 最终架构原则

Eunoia 的工作目录状态由 Agent Runtime 管理，而不是由 Bash 进程管理。

`run_command` 是无状态执行工具；`change_directory` 是修改 Task 执行上下文的状态操作。

每一次 Execution 都从 Task Context 读取一个确定的 CWD Snapshot，Sandbox Gateway 对其进行验证，再交给 OCI Runtime 执行。

因此：

- Agent 不需要记忆历史 `cd` 命令。
- Bash 不需要常驻。
- Task CWD 可以跨 Execution 持续存在。
- Task CWD 可以跨 Agent 重启恢复。
- 不同 Task 之间不会意外共享目录状态。
- 并发执行有明确的一致性语义。
- Sandbox 仍然是实际文件访问的安全边界。

**最终目标：让 Eunoia 的 Agent 拥有连续的工作目录体验，同时保留 One-shot Bash 的隔离性、可恢复性和可预测性。**
