# ADR 035 — 长任务检查点：编码任务压缩后的可继续性

**状态：** 已接受
**日期：** 2026-11-08
**相关：** ADR 014（agent loop）、ADR 023（coding-first 提示词）、ADR 028（执行历史与恢复）、ADR 030（每请求上下文预算）、ADR 032（模型轨迹与前缀缓存）、ADR 034（Subagent 与 Agent Team，规划中）

---

## 1. 决策

压缩不再只有一种「陪伴对话」模板，也不再只相信模型对工具执行的回忆。一次编码任务的检查点由两半组成：

1. **叙述**由摘要模型写：任务与约束、已完成、文件与改动理由、验证、待确认、下一步、任务板、关键决定与原话。
2. **工作证据**由系统从 `turn_events` 构建：真实写过的文件、跑过的命令、退出码、失败输出尾部、没有返回结果的工具调用、Team 任务板快照和证据索引。

证据追加在叙述之后，每次压缩都**从工具轨迹重建**，不把上一次的证据块原样滚入下一次；`splitCheckpoint` 在把旧检查点送回摘要模型前去掉证据块，避免两份事实竞争。两半都存放在现有的 `conversation_summaries.summary` 文本列中，结构由同一份文本解析回来，因此没有新表、没有 schema 迁移。

编码模板与陪伴模板按证据自动选择（`SESSION_CHECKPOINT_MODE=auto`），也可以强制。`SESSION_CHECKPOINT_ENABLED=false` 回到旧的单模板行为。

## 2. 背景

已有实现只解决「压缩之后还有没有上下文」，没有解决「压缩之后还能不能接着做」：

- 旧提示词固定为陪伴模板：当前主线、事实与偏好、人物关系、情绪、承诺、原话。它能保住一个人，但保不住半个重构：改过哪些文件、为什么改、测试过没有、哪个工具调用没有回来，全部丢失。
- 工具结果只存在于对话消息之外。摘要模型看到的只有 user/assistant 文本，工具调用与结果在 `turn_events` 里；即使提示词要求「保留测试结果」，模型也只能猜，猜出来的路径和退出码看起来同样可信。
- 前缀缓存解决**重复输入的复用**。它让同一段历史第二次发送更便宜，但压缩一旦发生，被裁掉的历史不会因为缓存而回来。检查点解决的是**压缩后能否正确继续**，两者不是一回事。
- Team 的任务板与根会话的压缩彼此独立：压缩后根模型不知道还有哪些任务没验收，新成员也不知道已经做过什么。

因此本决策把「任务状态」从模型的叙述里拆出来，变成可核对的事实；同时给任务板一个窄接口，使看板与检查点可以互相引用，而不是互相复制。

## 3. 两种模板

| | 陪伴模板 | 编码模板 |
|---|---|---|
| 保留 | 事实、偏好、关系、情绪、承诺、原话 | 任务与约束、已完成、文件与理由、验证、待确认、下一步、任务板 |
| 适用 | 没有工具轨迹的普通聊天 | 有工具轨迹、任务板或明显代码信号的会话 |
| 复用 | 原 `SUMMARY_SYSTEM_PROMPT` | 新增 `CODING_SUMMARY_PROMPT` |

`inferCheckpointMode` 的判定顺序是：有任务板 → 编码；有工具调用或读写检索 → 编码；消息里有代码围栏、路径或构建/测试命令 → 编码；否则陪伴。工具轨迹是强信号，文本判断只为「第一次工具调用之前就触发压缩」的窗口服务。错判的代价不对称：把陪伴对话判成工单，会伤害产品原本的用途，所以文本启发式保持保守。

`summaryPromptVersion(mode)` 分开计算两个模板的版本。评估记录因此能说明回复来自哪个模板，而不是只知道「摘要提示词变过」。

## 4. 为什么证据不由模型写

摘要模型擅长压缩意图和理由，不擅长回忆精确事实。让它在 2k token 里重述「测试通过了吗」会得到三种都不该出现的答案：编一个通过、把计划写成完成、或者省略失败。工具轨迹里这三件事都是可查的：

- `write` / `edit` 的 `file_path` 与结果状态 → 文件变更；
- `bash` 的命令、结果状态、`退出码 N`、输出尾部 → 验证结果；
- 有调用无结果，或结果状态是 `unknown` → 待确认。

`buildWorkLedger` 做纯函数配对，`createTurnEvidenceSource` 只负责从 `TurnStore` 读事件。配对规则刻意保留顺序：同一文件写两次、最后一次失败，与两次都成功是不同状态；孤立调用是「待确认」，不是失败也不是成功。

`unconfirmed` 是第三态，不是空值。一次命令没有结果行，既不能算通过也不能算失败；记录成任何一端都会让恢复路径做出错误决定。

## 5. 存储与兼容

检查点仍然是一份文本：

```
## 任务与约束
...
## 下一步
...

## 工作证据（自动记录）
### 文件变更
### 命令与验证
### 待确认
### 任务板
### 证据索引
```

不新增 `checkpoint JSON` 列或表，理由有三：

1. **只有一个读者。** 恢复的模型读文本；API 读结构。解析同一份文本得到结构，不会出现「表里的文件和文本里的文件不一致」。
2. **合并成本。** 本分支与 MCP（schema v11）、Subagent/Team 同时在改 schema 版本号。一个只为投影服务的迁移会让三条线上的版本号互相踩踏。
3. **回滚简单。** 关闭开关后旧代码只把整段文本当摘要，不认识附录也不会坏；旧检查点没有附录，解析为陪伴模板。

代价是结构化查询需要解析。`parseCheckpoint` 因此只认本模块写出的固定格式，解析失败时保留原文而不是丢弃。`GET /api/conversations/:id/checkpoint` 返回 `mode`、`sections`、`evidence`、边界序号和版本；未压缩过返回 `null`，不是 404 也不是空对象。

## 6. 预算与截断顺序

检查点仍受 `summaryTargetTokens` 约束，但截断顺序与旧实现相反：先为证据预留最多一半预算，再压缩叙述，最后拼接。若按旧方式先截断整段文本，被切掉的恰好是追加在末尾的事实——也就是这个功能存在的理由。证据本身也有上限（文件 40、命令 24、待确认 12、每个命令输出 400 字符），它是一份检查点，不是第二份轨迹。

## 7. 与 Team 任务板的衔接

`src/session/task-board.ts` 定义两个方向：

- **看板 → 检查点**：`TaskBoardSource.snapshot(userId, conversationId)` 返回 `TaskBoardSnapshot`。压缩时把任务 id、状态、验收条件、依赖和证据指针写进证据块；状态排序让已验收在前、未完成在后。
- **检查点 → 成员**：`renderTaskBrief({ task, checkpoint })` 给 fresh 成员一份有界简报：任务 id、验收条件、依赖，加上检查点的任务/文件/验证/下一步/证据索引。fresh 成员不继承根会话，这份简报就是它的上下文；它明确写着「不是用户的新指令」「不要重做已验收工作」。

本分支不实现 Team 运行时（`src/teams/` 目前只有领域类型与 store 契约，且在另一条未提交的分支上）。因此这里的交付是**端口、渲染、解析和测试**：Team 运行时落地时只需把 `TeamStore.listTasks(runId)` 适配成 `TaskBoardSnapshot`，并在构造 `SessionService` 时传入 `taskBoard`。`SessionService` 不 import `src/teams`，会话层不依赖协作层。

看板读取失败不让压缩失败：证据块缺任务板，叙述仍然保存。相反的选择会让一次审计查询故障把会话卡在超预算状态。

## 8. 压缩流程

1. 读取摘要边界与之后的原文，切出受保护尾部之外的 `older`；
2. 以 `older` 最后一条消息的 `createdAt` 为时间界，读 `turn_events`（最新优先、限量、再反转），构建 `WorkLedger`；读任务板快照；
3. `auto` 模式下用 `older`、轨迹、任务板判定模板；
4. 分块调用摘要模型：`previousSummary` 只含旧叙述，`mode`、`ledger`、`board` 随请求传入；
5. `composeCheckpoint` 为证据预留预算，截断叙述，追加证据块；
6. 旧检查点 + 被遮蔽消息的 token 必须大于新检查点，否则拒绝推进边界（沿用原有规则）；
7. 保存文本、`throughSeq`、`summaryTokens`、模板版本；日志记录模板、文件数、待确认数、任务板数。

第 2 步的读取是**事后再读**，不是压缩时从内存补。这正是重启后仍能生成证据的原因。

## 9. 失败与降级

| 故障 | 行为 |
|---|---|
| 轨迹读取失败 | `session.checkpoint_evidence_failed`，叙述照常保存，无证据块 |
| 任务板读取失败 | `session.checkpoint_board_failed`，证据块无任务板 |
| 摘要模型失败/空输出 | 不推进边界（原有行为） |
| 新检查点不比旧内容小 | 不推进边界（原有行为） |
| 检查点关闭 | 陪伴模板，不读轨迹与看板 |
| 旧检查点无附录 | 解析为陪伴模板，原文保留 |

## 11. 非目标

- 不做检查点的可视化编辑器；当前只提供只读 API。
- 不自动执行「下一步」，也不把下一步当指令注入。
- 不解析测试框架的结构化报告；失败输出尾部是诊断线索，不是机器可读的测试账本。
- 不在本分支实现 Team 运行时或任务板存储；只固定端口与文本契约。
- 不改变前缀缓存的 epoch/边界语义；证据块属于摘要文本，随压缩一起进入新的阶段边界。
