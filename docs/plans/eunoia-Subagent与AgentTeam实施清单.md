# Eunoia：Subagent 与 Agent Team 完整实施清单

状态：**部分实施**。核心运行时/任务板/预算/工作区/API/UI 已落地并有测试；MCP、审批绑定、图片授权、steering、候选发布端到端与 E01–E05 未完成，E06 真实运行未通过预算。逐项真实结果见[验收报告](../features/eunoia-AgentTeam验收报告.md)，不表示全部验收通过。

依据：[选型研究与源码链接](../research/agents/eunoia-Subagent与AgentTeam对照.md)，核对日期 2026-11-08。

## 1. 决策与交付边界

DSH 已有正式目录下的 Agent Team，实现为 Subagent 树加持久任务板。因此本次完整交付 **Subagent 运行时 + Agent Team 协作能力**：可只委派子任务，也可开启 Team、成员通信、任务依赖和验收。下面是同一次交付的工作分解，不是分期上线计划。

核心场景是同一用户、同一项目中，主 Agent 将可分离工作交给独立成员，成员有各自的模型上下文和工具循环，可以并行、交流、提交产物，由主 Agent 验收与集成。保留普通单 Agent 聊天。

不以多个角色提示词、并行只读工具、前端三个“思考中”动画代替独立 Agent。也不建设通用 Bench、模型质量评测平台或多用户组织协作系统；本次测试是功能契约、故障恢复与真实运行验收。

允许必要重构。复用原生 loop、ModelTurn、模型轨迹、Turn 幂等、沙箱、统一工具契约、MCP、媒体资源与权限服务，不建立第二套绕过检查的执行路径。旧 `docs/adr/001-single-agent.md` 保留历史，新增 ADR 明确其单 Agent 架构范围被本决策部分替代。

## 2. 完成定义

- [ ] 子成员是真实独立执行：独立内部会话、轨迹、模型请求、工具调用与取消信号；支持 fresh、fork、跟进、通信和关闭。
- [ ] Team 有持久成员树、任务板、任务依赖、并发认领、提交与验收；成员可互发消息。
- [ ] 两个可写成员使用隔离工作区；主 Agent 能检查、集成修改，并处理同文件冲突与源目录变化。
- [ ] 所有成员调用受统一权限、模型能力、媒体权限和总预算限制；MCP 行为同样纳入。
- [ ] 后台运行与 SSE 订阅解耦；刷新可恢复展示；崩溃可恢复记录，但不会自动重放未知副作用。
- [ ] 前端具备完整配置、观察、通信、审批、停止、结果审阅与冲突处理流程。
- [ ] 下文 T01–T60、E01–E06 全部有证据；未运行的容器或真实模型用例标记阻塞，不能算通过。

## 4. 领域对象与状态

必须区分“成员存在”“成员正在执行一轮”“业务任务通过验收”。复用一个 `completed` 布尔值会导致提前结束 Team。

| 对象 | 关键字段与规则 |
| --- | --- |
| Team | `id, ownerId, rootConversationId, enabled, configRevision`；根会话下一个稳定 Team，历史不因关闭开关删除 |
| TeamRun | `id, teamId, rootTurnId, inputHash, status, budgetId`；一次用户请求的一次协作；同一根会话不能并行启动两个运行 |
| Member | `id, teamId, parentMemberId, internalConversationId, name, profileSnapshot, permissions, workspaceId`；ID 稳定，名称不是权限凭据 |
| Activation | `id, runId, memberId, requestId, generation, status, checkpoint`；成员一次执行，空闲成员允许继续下一轮，同成员不并发执行两轮 |
| Task | `id, runId, revision, title, specification, acceptance, required, dependencies, ownerId, status, writeScopes` |
| TaskAttempt | `id, taskId, activationId, generation, lease, baselineId, submission, review`；重新认领创建新 attempt，保留旧记录 |
| Message | `id, teamId, runId, senderId, recipientId, clientMessageId, payloadRef, sequence, state`；服务器确定发件人 |
| Artifact | `id, attemptId, kind, manifest, baseHashes, contentHashes, testEvidence`；内容不可变，不能依赖临时路径作为唯一结果 |
| Event / Outbox | 递增事件序号、幂等键、事件类别、受控数据；与状态修改同事务落库 |

状态约束：

- Member：`provisioning / idle / active / closing / closed / failed`；关闭后的名称不可被冒用为原成员 ID。
- Activation：`queued / running / waiting / succeeded / failed / interrupted / unknown`；`succeeded` 只说明这次执行正常结束。
- Task：`pending / running / submitted / accepted / failed / cancelled`；提交附证据，验收才能变成 accepted。拒绝提交后重新进入 pending，并创建新 attempt；旧提交不可覆盖。
- Task 是否 ready 由“pending 且依赖均 accepted”计算，不单独存一个容易过期的 ready 字段。必需任务失败或被取消，不能视为满足依赖。
- TeamRun：`queued / running / pausing / paused / waiting_user / stopping / succeeded / failed / cancelled / needs_reconciliation`。各状态允许的动作列成状态迁移表并测试。

成功条件：全部 required 任务 accepted；没有未处理冲突、未知副作用、待决审批；必需产物存在且哈希匹配；成员中必要的执行已结束。可选任务可以显式取消并记录原因，不能偷偷删除后宣布成功。

## 5. Subagent 运行时

### 5.1 创建、上下文和模型

- [ ] `spawn` 返回稳定成员 ID 和执行 ID；成员初始化失败释放预留容量，留下可读错误，不产生幽灵成员。
- [ ] fresh 为默认模式：只传任务说明、必要背景、选定资料与授权资源，不复制整个主会话。
- [ ] fork 从指定的已提交轮次快照开始；工具调用与结果完整配对，不包含正在生成的 assistant、未决工具或未提交消息。父子快照写时分离，子修改不能污染父历史。
- [ ] fork 的上下文授权独立校验：父轨迹里已有的敏感工具输出和资源不因“继承历史”自动对低权限成员开放。无法安全裁剪且保持协议完整时拒绝 fork，提供 fresh 与显式资料选择。
- [ ] 普通跟进继续同成员上下文；另建子成员才改变上下文隔离。忙碌成员的跟进排队，显式 interrupt 才中断当前执行。
- [ ] `ModelProfile` 和 provider 可配置；默认继承当前模型配置快照，允许用户授权的成员配置覆盖。运行中变更记录新 epoch，不静默替换已有请求。
- [ ] 模型不支持必需的工具或图片时，先预检：拒绝该成员配置，或让用户选择具备能力的模型。不能删掉图片继续声称任务等价完成；不能靠模型名称猜能力。
- [ ] 跨协议 fork 通过现有规范轨迹转换；不能转换的 provider 私有内容不原样发送，明确要求改用 fresh 或同协议配置，不能无提示损失关键上下文。
- [ ] 子执行默认不自动写入用户长期记忆；记忆读写也属于显式权限。成员的任务聊天不会混入根会话普通消息列表。

### 5.2 生命周期和工具

统一提供 `agent_spawn`、`agent_followup`、`agent_list`、`agent_send_message`、`agent_wait`、`agent_interrupt`、`agent_close`。名称可按项目风格调整，但要有一个稳定工具目录和结构化错误码。

- `interrupt`：停止当前 activation，成员保留，可以跟进。
- `close`：停止并关闭成员，拒绝新跟进；其子成员按显式级联规则收束，不能遗留后台模型和容器进程。
- `stop run`：停止整次协作及其子树，同时保留日志、产物与未知副作用状态。
- `wait`：明确等待消息、指定执行结束或指定任务条件；带截止时间与取消信号，返回原因及游标。不用无限轮询消耗模型 Token。
- 多个监听者可以看同一结果，但对模型上下文的结果注入有幂等键，不能一条通知重复附加多次。

普通 Subagent 即使 Team 任务板关闭也可使用。关闭 Team 只影响后续任务调度和工具可用性，保留记录；界面须另有明确的“停止运行”，不能让开关同时暗含销毁行为。

## 6. 邮箱、任务板与调度

### 6.1 消息

- [ ] 只允许同一 Team、同一 owner 范围内的当前合法成员互发消息；服务端从调用上下文确定 sender，拒绝伪造和越权 ID。
- [ ] `clientMessageId + sender + recipient` 幂等；同键不同内容返回冲突。发送成功表示持久接收，不表示接收模型已经读过。
- [ ] 区分 accepted、注入接收方轨迹、处理完成；轨迹提交与消息消费游标须可恢复，防止崩溃后漏消息或重复注入。
- [ ] 忙碌成员在安全的下一模型步骤接收；空闲成员可由消息触发排队激活；已关闭成员返回明确错误。消息不能插到一个未配对的工具调用中间。
- [ ] 消息是带来源的协作数据，不能冒充用户、system 或 developer 指令，不能修改权限和预算。模型适配器负责合法消息编码。
- [ ] 限制单条大小、队列长度、消息总量、自动激活次数与广播扇出；默认没有无限广播。成员互相“请再确认”不能形成无界自激循环。

### 6.2 任务板

模型工具至少提供 create/list/get/update/claim/submit/review，允许合并 schema，但服务层必须保留明确的动作与授权。

- [ ] 创建时填写可检查的目标、验收条件、required 和依赖；分页读任务，不把整个看板塞进每次 system prompt。
- [ ] 同一 TeamRun 内依赖形成 DAG，禁止自依赖、循环、跨运行或不存在的依赖。修改依赖也要验证；已被依赖的任务取消应触发显式阻塞处理。
- [ ] 所有修改携带 `expectedRevision`；CAS 失败返回当前版本。多个成员同时认领最多一个成功，不靠进程内数组锁。
- [ ] 普通成员只能认领 ready 任务、修改自身允许的字段、提交自己的 attempt；主 Agent/用户负责重新分配和验收，成员不能自行放宽验收条件后通过自己的交付。
- [ ] 成员资格来源唯一：当前 Team 成员服务；历史 roster 不是授权依据。成员树不能跨 Team 挂接或形成环。
- [ ] writeScopes 是调度提示和可选路径权限输入，不是锁本身。实际文件权限必须由文件网关、命令沙箱和 MCP 策略共同落实。
- [ ] 看板提交与唤醒分开：事务写任务和 outbox，调度器按事件幂等唤醒。单纯更新标题不得启动一个执行；ready 变化仅启动已允许自动派发的任务。

### 6.3 并发、租约和等待

- [ ] 任务 attempt 和 worker 有租约、心跳与递增 generation；状态写回检查 generation，过期 worker 不能提交新结果。
- [ ] generation 不能阻止已在运行的外部命令。重分配写任务前，必须确认旧进程/容器已终止；外部副作用未知则进入 needs_reconciliation，不自动再发同一动作。
- [ ] 等待子成员不占模型请求许可。成员数量、活跃 activation、进行中的模型 HTTP 请求是不同计数；不能因主 Agent 等待占满许可导致子成员永远跑不起来。
- [ ] 协调等待使用专门的可取消等待契约，不误用普通短工具超时。主模型提前生成最终答案时，服务检查任务与必需子执行；尚未满足完成条件就保留候选答案并等待/继续协调，不能先标成功，也不能靠无意义模型轮询维持运行。
- [ ] 调度器有用户/全局上限、公平队列和退避；暂停派发后保留队列。无需实现分布式集群，但重复唤醒、重启和两个本地 worker 抢同一记录必须安全。
- [ ] 暂停先进入 pausing：禁止新模型请求和新工具派发，已有动作收束后 paused；未知副作用不能伪装成已安全暂停。恢复需重新核对 generation、权限与预算。

建议默认：每 Team 最多 4 名成员（含主 Agent）、最多 3 个同时模型请求、最大子树深度 2、每次运行最多 32 次 activation、64 次模型请求、256 条任务、128 条协作消息。部署可调，但客户端和模型不能自行提高上限。默认值是防失控的工程选择，不是性能结论。

## 7. 工作区、产物和集成

### 7.1 隔离和基线

- [ ] 以现有 copy 工作区为基础，为每个可写成员创建独立目录和沙箱；只读成员使用只读快照。禁止两个写成员直接挂载用户源目录。
- [ ] 快照记录源版本、已授权的未提交/未跟踪文件及内容哈希；默认排除密钥、忽略目录和越界符号链接。用户现有修改保留原样，不能 stash/reset/clean/commit 用户仓库。
- [ ] Git 项目需要 Git 操作时，为副本建立独立 Git 元数据，隔离 hooks、凭据与配置；不要仅创建 worktree 后把共享 `.git` 暴露给所有容器。非 Git 项目也支持快照与差异集成。
- [ ] 执行环境声明依赖安装方式、网络权限和端口分配。共享缓存只读或内容寻址；不得共享可写依赖目录让成员修改另一个成员的执行环境。
- [ ] 每个 artifact 记录路径、增加/修改/删除类型、基线与结果哈希；处理重命名、二进制、执行位、大小限制和符号链接策略。禁止目录穿越和产物路径逃逸。

### 7.2 集成与验收

- [ ] 成员提交修改产物，不能自行向用户工作区发布。主 Agent 在独立集成工作区按基线应用，通过版本检查或三方合并；有冲突保留双方内容，禁止最后写入者覆盖。
- [ ] reviewer 在实际集成候选快照验证，证据绑定候选哈希；之后有新修改使相关验证失效。测试成功不等于批准发布。
- [ ] UI 能查看差异、冲突和验证证据；用户或获授权主 Agent选择解决方案，解决后的快照重新验证，任务才可 accepted。
- [ ] 向源目录应用前核对相关文件当前哈希。用户期间改动导致基线过期，停在冲突状态，不能覆盖；无关文件变化不必拒绝全部集成。
- [ ] 发布用持久 journal、受控路径锁、逐文件校验和原子替换。多文件操作不可宣称文件系统天然全局原子；故障时记录已应用集合，恢复只回滚仍匹配本次写入哈希的文件，其余转人工协调。
- [ ] 发布重试使用同一幂等键，不重复应用；无 Git 自动提交/推送要求。远程发布若以后使用 MCP，沿用其权限与未知副作用策略。
- [ ] 清理有 TTL 和引用保护；活跃任务、未验收结果、冲突与未知状态相关工作区不能被提前删掉。关闭成员不等于删产物。

## 8. 权限、MCP、媒体和 Token

### 8.1 权限与副作用

有效权限取部署上限、用户授权、根运行、成员角色、任务 attempt 的交集。子成员的权限不能大于父级上限；模型传入的 `role: reviewer` 不构成授权。

- [ ] 所有工具经过同一个策略入口；文件读写、命令、网络和 MCP 都带 `teamId/runId/memberId/activationId/taskAttemptId/generation`。
- [ ] 审批显示实际成员、任务、工具、目标账号/路径与参数摘要，批准绑定参数哈希、作用域和有效代次；不能把主 Agent 的宽泛批准继承成子成员通行证。
- [ ] MCP 连接和凭据由服务器管理，成员只获得授权工具句柄，不得到密钥文本。stdio 进程绑定对应工作区和运行身份，不能共用可写 cwd 或越权资源缓存。
- [ ] MCP elicitation、Tasks、审批等待归属正确成员；父运行停止能取消等待。外部服务不能确认取消时记录 unknown，禁止成功假象和自动重发。
- [ ] 沙箱出口、资源限额、审计脱敏继续生效。日志中的同一调用能追踪到子任务，不能只显示根 conversationId。

### 8.2 图片与上下文

- [ ] 子会话不得通过放宽全局 conversationId 校验拿到私有图片。建立显式、可撤销的 Team 资源授权，限定 owner、资源、目标成员/任务、用途和期限。
- [ ] fresh/fork 的附件在派发前验证可访问性和模型能力。图片只能通过既有媒体代理或受控资源句柄解析，不能把密钥 URL 放进成员消息。
- [ ] 子结果默认注入摘要、证据和 artifact 引用；不自动把每个成员完整轨迹复制回根上下文。用户可以展开公开执行记录，不展示私密推理或凭据。
- [ ] 保持稳定的成员工具/schema 和策略前缀；看板、消息等动态内容以增量加入。fork 可能复用前缀不等于厂商承诺命中缓存，不据此提前抵扣预算。

### 8.3 全队预算

- [ ] 团队请求、输入、输出与费用账本覆盖主成员、全部子成员、工具后的模型续轮、跟进、重试和摘要；每次真实 provider 调用有唯一 request/attempt 标识。
- [ ] 每次请求先进行上下文可容纳预检，再从全队剩余预算原子预留输入估算与最大输出；两个成员不能各看到同一剩余额度然后同时透支。
- [ ] 文本与图片估算复用既有模型策略；独立成员各自实际发送同一图片，要分别计入各次请求。provider usage 返回后结算；缓存命中是输入的一部分，不能重复加总。
- [ ] usage 缺失、调用超时或取消但可能已计费时，保留保守预留并标记不完整；不得按 0 结算后继续无限派发。提供后续对账入口。
- [ ] 请求次数与 token 上限是硬派发限制。费用估算带价格来源、版本和 unknown 状态；不能把客户端预算描述成绝对账单限额。
- [ ] 成员预算不能靠再 spawn 绕过。预算用尽停止新派发并报告未完成项，已有副作用按恢复规则收束；汇总展示实际/估算、缓存/未缓存和不完整统计。

默认总 Token 上限沿用部署预算配置，Team 创建时必须明确显示并保存；未配置预算不得悄悄等于无上限。不要把每个成员的单请求预算直接当成全队预算。

## 9. 持久化、恢复和幂等

- [ ] 存储对象、索引、外键、状态变更、outbox 和预算有事务边界；迁移兼容现有会话/轨迹/媒体数据，并提供备份与恢复说明。
- [ ] 创建运行的幂等键绑定 owner、根会话和输入哈希；重复请求返回同一运行，不再创建成员。跟进、消息、认领、提交、验收、发布也各有幂等策略。
- [ ] 进程启动扫描旧 generation、未完成调用、租约和发布 journal。只重放已经提交的事件，不因为看到 running 就重新执行命令或 MCP。
- [ ] 纯只读、可证明无副作用的步骤可按策略重试；写入或未知调用必须先对账。失去模型响应也不意味着此前工具从未执行。
- [ ] 成员历史和 pending inbox 可恢复；继续执行创建新 activation，冻结的模型/工具配置若失效，显示阻塞与重新选择入口，不静默切成别的模型。
- [ ] late callback 必须检查 run 状态和 generation；已经停止的运行不能被迟到结果改为 succeeded，也不能继续集成文件。
- [ ] 生命周期与 SSE 断开解耦。当前 `server.ts` 在连接关闭时 abort 普通聊天，需要将 Team 运行移到持久作业服务；普通聊天是否保持原断开语义单独回归。
- [ ] 根轮次和成员轮次均使用现有互斥/幂等基础。用户在运行中追加指令走专门 steering 队列；不能通过第二个普通聊天请求破坏根会话互斥。
- [ ] 成功、失败、部分完成、取消和待对账都返回已完成/未完成任务及证据，不能只返回“子 Agent 出错”。

## 10. API 与前端完整流程

实际路径可按既有路由调整，以下操作及语义不可缺失。统一进行 owner 校验、请求校验、幂等处理与结构化错误映射。

| API 操作 | 主要约束 |
| --- | --- |
| 读取/更新 Team 配置 | `expectedRevision`；模型、成员上限、模式和预算预检；历史运行不被静默改写 |
| 创建运行、读取运行快照 | 根 requestId 幂等；返回可订阅的 runId 与初始事件游标 |
| 成员列表、详情、公开轨迹 | 不泄露密钥或私密推理；分页，子会话不出现在普通会话列表 |
| spawn、followup、send message | 同一服务支持模型工具和用户 UI；区分用户消息与成员消息来源 |
| pause/resume/stop、interrupt/close | 作用域清晰；异步操作返回当前状态，不能在进程还没停止时宣称完成 |
| 任务 create/update/claim/submit/review | CAS、资格与状态机检查；过期版本返回冲突及当前值 |
| 产物 diff、验证、冲突解决、应用 | 受控路径与哈希；发布幂等；不能用任意本地路径下载文件 |
| steering、审批与对账 | 绑定具体运行/成员/动作；旧页面操作不能批准新 generation |
| SSE 事件及补拉 | 单运行递增 eventId，支持 Last-Event-ID；事件过期返回完整快照和新游标，无静默漏事件 |

前端必须有：

- [ ] Team 开关及配置入口；直接委派也可使用 Subagent。显示成员模型、权限与总预算，不要求用户理解 provider 私有参数。
- [ ] 主对话内显示运行摘要；展开成员树、独立状态、任务进度、预算和失败原因，不展示虚构“思考过程”。
- [ ] 共享任务板显示依赖、归属、状态、提交、验收条件、证据；抢占冲突时刷新当前版本，不吞错误。
- [ ] 成员详情可看公开执行轨迹、发送跟进或 `@成员` 消息、停止本轮或关闭成员。`@` 解析为稳定成员 ID；名称重名、改名、历史成员不可误投。
- [ ] 明确“暂停派发”“停止本轮”“关闭成员”“停止整队”的作用与状态。停止后展示部分产物和未决副作用。
- [ ] 审批卡片显示具体子成员和动作；差异审阅、冲突编辑、重新验证和应用结果都可完成。
- [ ] 刷新或网络重连先补事件，再接流；同事件幂等更新，不能把恢复当成新建运行。多个页面同时观察不触发重复执行。
- [ ] 键盘可用、可访问标签、390px 窄屏无横向页面溢出；界面默认收起大日志，长列表分页。

## 14. 验收报告与可介绍的亮点

DSH 交付 `docs/features/eunoia-AgentTeam验收报告.md`，至少包含：代码提交、环境/模型配置（脱敏）、迁移结果、T/E 每项结果和证据位置、失败与未执行项、已知限制、复现命令、实际资源/Token 统计和清理情况。将本计划的状态更新为“已实施并验收”必须有报告支撑。

可在全部验收后介绍的能力：

1. **可替换模型的协作运行时**：Subagent/Team 属于 Harness 编排，成员通过统一模型端口运行，不绑定某个厂商的多 Agent 产品。
2. **上下文隔离和显式协作**：fresh/fork、持久邮箱和共享 DAG 让任务归属可查，结果提交和验收分离。
3. **并行修改可控集成**：隔离工作区、带基线的产物和候选验证，防止多个成员互相覆盖以及覆盖用户修改。
4. **全队预算与权限闭环**：成员、图片、MCP、审批和重试都纳入同一个权限与预算体系。
5. **有证据的恢复**：事件重连、代次隔离、未知副作用对账，使“刷新继续看”和“崩溃不乱重跑”有明确边界。

暂不能写“已降低 X% 成本/加快 X 倍/效果优于单 Agent”。这些需要另做同任务、同预算的质量与性能实验，本次功能验收不产生这种结论。
